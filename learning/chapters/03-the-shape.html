Chapter 03 · Part I

The shape

How a stateless command-line tool, Linux user services, and Google's auth proxy fit together — and the four architectural decisions that keep the design flat.

The system at a glance

Before reading code, look at how control and data flow through the operating system. The program is not a daemon, not a background worker, and not a database driver. It is a short-lived control plane that runs for milliseconds, instructs the Linux service manager to start or stop proxies, inspects system state, and exits.

┌─────────────────────────┐ spawn / poll ┌──────────────────────────┐ │ Omarchy Quickshell bar │ ───────────────────► │ cloud-sql-tracker │ │ (or Terminal / CI) │ ◄──── JSON/status ── │ (stateless Rust binary) │ └─────────────────────────┘ └────────────┬─────────────┘ │ D-Bus / zbus (user bus) │ ▼ ┌──────────────────────────────┐ │ systemd --user │ │ cloud-sql-proxy-.service │ │ (transient Unit, 1 per DB) │ └──────────────┬───────────────┘ │ spawns / supervises │ ▼ ┌──────────────────────────────┐ │ Google cloud-sql-proxy (Go) │ │ 127.0.0.1:15432+ │ └──────────────────────────────┘

Every long-lived process is Google's official cloud-sql-proxy binary. Each proxy instance is supervised by systemd --user as a transient service unit. cloud-sql-tracker coordinates these units over D-Bus, probes local ports, and emits structured status for scripts and desktop bars.

The entry points

The entire binary entry point in src/main.rs is thirteen lines long. It does not contain command dispatch, argument parsing, or business logic. It invokes the library crate's command-line interface and exits with the returned status code.

//! cloud-sql-tracker — stateless control plane for cloud-sql-proxy processes.
//!
//! This binary does **not** implement the Cloud SQL tunnel. It starts, stops,
//! and reports on Google's `cloud-sql-proxy`, driven by a user config file and
//! systemd --user transient units.
//!
//! See README.md and docs/DESIGN.md. Behavior lives in the library crate
//! (`src/lib.rs`); this binary is only `exit(cli::run())`
//! (`docs/modules.v1.md`, "`cli` — thin shell (clap)").

fn main() {
    std::process::exit(cloud_sql_tracker::cli::run());
}

Key Linux concepts for newcomers

If you have not written native Linux system utilities before, four terms appear throughout the codebase:

systemd unit
A resource managed by Linux's system and service manager. Service units define how to launch an executable, restart policies, environment variables, stop timeouts, and cgroup tracking.
transient unit
A dynamically created, in-memory systemd service created at runtime over D-Bus (named like cloud-sql-proxy-fe-dev.service). It exists in memory (on a tmpfs filesystem under /run/user/<uid>/) without requiring persistent unit configuration files on disk.
D-Bus and the user bus
D-Bus is a standard Linux inter-process communication (IPC) system. The user bus is a per-login-session D-Bus daemon running under your unprivileged user account. Programs query properties and invoke methods on systemd's user manager without needing sudo or root privileges.
Application Default Credentials (ADC)
Google Cloud's standard credential discovery strategy. Client libraries and cloud-sql-proxy automatically read credentials from the GOOGLE_APPLICATION_CREDENTIALS environment variable or the default login file at ~/.config/gcloud/application_default_credentials.json created by gcloud auth application-default login.

The four Architecture Decision Records (ADRs)

Every non-obvious design choice in this project is captured in an Architecture Decision Record under docs/adr/. When in doubt about why something is built a certain way, consult these four ADRs.

ADR 0001: Stateless CLI over systemd --user

Decision

Pick: A short-lived Rust CLI that communicates with systemd --user over D-Bus.
Why: Survives desktop shell restarts, requires no background tracker daemon, and provides a single contract (argv + JSON) for terminals, scripts, and desktop plugins.
Discarded: Process management inside the QML desktop bar; a persistent tracker background daemon.
Unchanged: Google's cloud-sql-proxy remains the actual tunnel binary.

Why not manage proxy processes directly inside the desktop bar plugin? Quickshell and desktop bars restart whenever their configuration changes or the compositor reloads. If the bar owned the child process handles, restarting the bar would terminate every database tunnel mid-query.

Why not run a long-lived cloud-sql-tracker daemon? A daemon introduces Unix domain socket IPC, state synchronisation bugs, daemon crash recovery, and the question of "who supervises the supervisor?" For ~7 proxy processes polled every few seconds, a stateless CLI that reads live operating system state is significantly simpler and more robust.

ADR 0002: ADC-only authentication

Decision

Pick: Application Default Credentials (ADC) as a hard requirement.
Why: Developers on Linux workstations already authenticate with Google Cloud using gcloud auth application-default login.
Discarded: Custom OAuth token exchange, service account JSON key file management, and bespoke auth flags.
Unchanged: The proxy binary handles all Google Cloud token refreshes natively.

The control plane forwards only the operator's HOME and optional GOOGLE_APPLICATION_CREDENTIALS environment variables into the transient systemd units. The doctor command treats missing or unreadable ADC credentials as a hard failure.

ADR 0003: Local health signals

Decision

Pick: Health state is derived strictly from our systemd unit's state and a local TCP connect accept on 127.0.0.1:<port>.
Why: Connecting to the remote Cloud SQL database requires database credentials (passwords/IAM database users) that the control plane does not and should not hold.
Discarded: Upstream database pings; proxy HTTP health check endpoints (which cause port collisions across multiple proxies in v1); orphan process adoption.
Unchanged: Start commands verify local port readiness before returning.

If a proxy process is running on the configured port but was launched manually outside of our managed systemd unit, the control plane classifies it as a Foreign process and reports a port_conflict error. It never silently adopts unmanaged processes.

ADR 0004: Native Linux I/O

Decision

Pick: Native Rust crates and Linux APIs (zbus for D-Bus, procfs and std::net::TcpStream for sockets/processes).
Why: Programmatic interfaces provide structured types and fail reliably, eliminating brittle scraping of shell pipelines like ss, pgrep, or systemctl stdout.
Discarded: Shelling out to systemctl or ss for control and inspection.
Unchanged: journalctl is still used for cloud-sql-tracker logs because formatted log extraction is journalctl's primary design.

The zero-memory superpower

Notice what is missing from this project: there is no state.json, no SQLite database, and no cache directory. The control plane holds zero persistent memory across invocations.

When you run cloud-sql-tracker status --json, it reads the static configuration file, inspects the live systemd user manager over D-Bus, probes the configured TCP ports, passes the observations through a pure reconciliation algorithm, outputs the resulting Status document, and terminates.

Resilience benefit

If the computer suffers an unexpected power loss, kernel crash, or hard shutdown, no cleanup is required on next boot. Transient unit definitions disappear automatically because they reside in memory (tmpfs). The next boot starts with a clean slate, and every connection is predictably reported as stopped until manually started.

Check yourself

  1. Why does cloud-sql-tracker supervise proxies via systemd --user instead of spawning them directly as child processes of the desktop bar plugin?
    Answer

    Spawning proxies directly from the desktop bar would cause all database tunnels to crash whenever the UI reloads or the desktop compositor restarts. Supervising them under systemd isolates proxy lifetimes from UI lifecycles.

  2. Why does the project refuse to adopt a running cloud-sql-proxy process that was launched outside of its managed systemd unit?
    Answer

    An externally launched process has unverified launch flags and lacks systemd lifecycle supervision. Treating it as a foreign port conflict avoids subtle bugs caused by managing processes the control plane did not configure.

  3. How does having zero persisted state files make the control plane resilient against sudden power failures or system crashes?
    Answer

    Because transient unit state lives entirely in tmpfs and no state file is written, there is no corrupted or stale state to clean up after a hard reboot. The next run re-evaluates reality directly from the OS.
