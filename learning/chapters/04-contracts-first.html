Chapter 04 · Part II

Contracts first

How machine-readable JSON Schemas, golden fixtures, and layered verification prevent drift between documentation, CLI output, and UI consumers.

The contract-first philosophy

In many software projects, machine interfaces are an afterthought: developers write code, export a data structure with serde, and reverse-engineer documentation from the output. When changes happen, documentation silently drifts from reality, breaking external consumers like desktop widgets or automation scripts.

This project inverts that workflow. Every boundary between the control plane and the outside world is specified and locked before code is written. The contract is the specification, the test suite is the enforcer, and the Rust code is the implementation.

The Contract Trio rule

For every machine-readable JSON boundary in the project, the repository maintains exactly three synchronized artifacts known as a Contract Trio:

Artifact Location Purpose
1. Prose specification docs/*.v1.md Human-readable normative rules, field meanings, error catalogs, and transition tables.
2. JSON Schema schemas/*.v1.json Machine-readable Draft 2020-12 JSON Schema defining types, required fields, constraints, and rejection rules.
3. Golden example examples/*.json A concrete, realistic JSON snapshot demonstrating valid fields and structure.
The Invariant

The Same-PR Rule: Touching any JSON field, enum variant, or validation rule requires updating the prose document, the JSON Schema, and the golden example together in the same pull request. A schema change without updated documentation or an example is rejected by review.

The three JSON Contract Trios

The control plane defines three distinct JSON surfaces:

  1. Status Document Trio:
    • Prose: docs/status-document.v1.md
    • Schema: schemas/status.v1.json
    • Golden: examples/status.v1.json
    • Produced exclusively by cloud-sql-tracker status --json. This is the primary telemetry consumed by the Omarchy desktop bar widget.
  2. Configuration Trio:
    • Prose: docs/config.v1.md
    • Schema: schemas/config.v1.json
    • Golden: examples/connections.json
    • Defines the schema for ~/.config/cloud-sql-tracker/connections.json. Enforces strict key validation (unknown keys are rejected with exit code 2).
  3. Doctor Report Trio:
    • Prose: docs/doctor.v1.md
    • Schema: schemas/doctor.v1.json
    • Golden: examples/doctor.v1.json
    • Produced by cloud-sql-tracker doctor --json. Provides preflight checks for system readiness (config, proxy binary, user bus, credentials, journal, and ports).
Plain-Text and Argv Surfaces

Non-JSON interfaces (like cloud-sql-tracker logs <id> and command-line argument parsing) do not have a JSON Schema. They are specified with prose (e.g. docs/logs.v1.md, docs/cli-contract.v1.md) and companion text snapshots (e.g. examples/logs.v1.txt).

Schema version vs binary version

Look at the top of any generated Status document or Doctor report. You will see two version fields:

{
  "version": 1,
  "ts": "2026-08-20T19:45:00+02:00",
  "cli_version": "0.1.1",
  "running": 1,
  "starting": 0,
// ...

examples/status.v1.json:1–6

These two numbers serve completely different purposes:

  • version (integer, currently 1): The Schema ID of the document format. It bumps only on breaking structural changes (such as renaming or removing a required field, or altering an enum's semantics). Additive optional fields do not bump version.
  • cli_version (string, e.g. "0.1.1"): The semver version of the compiled binary, derived directly from CARGO_PKG_VERSION in Cargo.toml.

Correspondingly, the JSON Schema mandates these exact constraints:

  "required": [
    "version",
    "ts",
    "cli_version",
    "running",
    "starting",
    "error",
    "stopped",
    "total",
    "groups",
    "connections"
  ],
  "properties": {
    "version": {
      "type": "integer",
      "const": 1,
      "description": "Status document schema id. Breaking shape changes bump this integer."
    },
    "ts": {
      "type": "string",
      "format": "date-time",
      "description": "RFC 3339 timestamp when the snapshot was built."
    },
    "cli_version": {
      "type": "string",
      "minLength": 1,
      "description": "Semver of the cloud-sql-tracker binary that produced this document."
    },

Two verification layers: Layer 1 vs Layer 2

How do we guarantee that code, goldens, and schemas never diverge? The repository splits contract verification into two distinct layers.

Layer 1: Offline Schema Validation

Layer 1 tests the contract artifacts directly using check-jsonschema. It verifies that every golden example file in examples/ strictly validates against its corresponding JSON Schema in schemas/. It runs fast, requires no Rust compilation, and executes in Git pre-push hooks and CI.

#!/usr/bin/env bash
# Layer 1 of issue #23: golden examples vs JSON Schemas.
# This script is the pair registry. Call it from mise, hk pre-push, and CI.
# Do not add logs.v1.txt (plain text). Do not close #23 on this check alone.
set -euo pipefail

root="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$root"

if ! command -v check-jsonschema >/dev/null 2>&1; then
  echo "check-jsonschema not on PATH. Run: mise install" >&2
  exit 1
fi

check() {
  local schema="$1"
  local instance="$2"
  echo "validate '${instance}' against '${schema}'"
  check-jsonschema --schemafile "${schema}" "${instance}"
}

check schemas/status.v1.json examples/status.v1.json
check schemas/config.v1.json examples/connections.json
check schemas/doctor.v1.json examples/doctor.v1.json

scripts/validate-contracts.sh:1–24

Layer 2: Real Binary Stdout Proof

Layer 1 only proves that static JSON examples match the schema. It does not prove that the compiled Rust binary outputs valid JSON!

Layer 2 (implemented in tests/cli_json_contracts.rs) executes the actual compiled binary (via CARGO_BIN_EXE_cloud-sql-tracker), captures its live stdout for status --json and doctor --json, and validates the live output against the schemas using the jsonschema crate.

Common Pitfall: In-process Serde Tests

Testing serde_json::to_string(&struct) inside a unit test is not Layer 2 verification. In-process tests bypass CLI flag parsing, stdout pipe buffering, formatting wrappers, and real process exit paths. Only spawning the compiled executable proves the external contract.

Check yourself

  1. What are the three components of a Contract Trio, and what rule governs changes made to them?
    Answer

    A Contract Trio consists of the prose document in docs/, the JSON Schema in schemas/, and the golden example in examples/. Any change to one must update all three together in the same pull request.

  2. Why does the Status document contain both a version field and a cli_version field?
    Answer

    The version field represents the integer schema format ID which only bumps on breaking schema changes. The cli_version field represents the semver release version of the compiled Rust binary.

  3. Why is in-process serde serialization testing insufficient to satisfy Layer 2 contract verification?
    Answer

    In-process serialization only tests Rust data structures in memory. Layer 2 executes the built binary as a real subprocess to validate that its actual stdout matches the JSON Schema under real runtime conditions.
