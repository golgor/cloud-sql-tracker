Chapter 06 · Part II

Reconcile: the pure heart

One observation in, one Health state out. No I/O, no clock reads, and no hidden state — the pure decision engine that evaluates machine truth for every database connection.

The mental model: read-only classification

Most service managers couple decision-making with side effects. A background daemon polls a process, decides it looks unhealthy, issues a kill signal, writes a timestamp to a state file on disk, and restarts the child. When state and effects intertwine, testing requires complex mocks, timing races multiply, and unexpected crashes leave stale state files that poison subsequent boots.

cloud-sql-tracker avoids this entirely. At the core of the system is Reconcile: a pure mathematical function that maps machine observations to a Health state and status row fields.

config identity + Unit snapshot + port probe + listener PID + clock │ │ │ │ │ └──────────────────┴────────┬────────┴────────────────┴──────────┘ ▼ reconcile() ← pure: same inputs ⇒ same output ▼ StatusRow fields (HealthState, Source, pid, port_open, uptime_sec, error)

Reconcile is strictly read-only classification. It is not an active controller loop. It does not spawn processes, kill processes, read files, or query the Linux kernel. Callers gather the raw signals from the operating system, package them into an Observation struct, and pass them into reconcile() alongside a timestamp.

Pure Core vs. I/O Shell

In accordance with ADR 0003, health in v1 is strictly local: our managed systemd unit state plus local TCP socket acceptance. Reconcile evaluates this local reality deterministically. Given identical inputs, it will always return the exact same output.

The observation inputs

To classify the health of a Connection, Reconcile needs to know what systemd sees and what the local network stack sees. These facts are captured in two sub-structures in src/reconcile.rs:

/// One Connection's observed signals at one instant
/// (`docs/reconcile.v1.md`, "Observation inputs"). `commands` builds this
/// from `supervisor::show` + `port::observe`; Reconcile only classifies it.
#[derive(Debug, Clone)]
pub(crate) struct Observation {
    pub(crate) unit: UnitObservation,
    pub(crate) port: PortObservation,
}

/// What we know about a Connection's systemd `--user` Unit.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub(crate) struct UnitObservation {
    pub(crate) state: UnitState,
    /// Main proxy PID if the Unit currently has a live process.
    pub(crate) main_pid: Option,
    /// When the current start attempt began (systemd's
    /// `ExecMainStartTimestamp` or equivalent). `None` when the Unit is
    /// [`UnitState::Idle`] or has no known start attempt yet.
    pub(crate) started_at: Option,
}

/// A Unit's `ActiveState`, simplified to what Reconcile's truth table
/// distinguishes (`docs/reconcile.v1.md`, "Truth table").
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub(crate) enum UnitState {
    /// Not loaded (including "unit not found"), or loaded and
    /// `inactive`/`dead`. Not failed.
    Idle,
    Activating,
    Active,
    Deactivating,
    /// `ActiveState=failed`. See `docs/reconcile.v1.md`,
    /// "Clean stop vs failed unit".
    Failed(FailureSignal),
}

Vocabulary: Systemd Unit

A systemd unit is a Linux service unit managed by the systemd initialization and service manager; in this project, proxies run as transient units under the user's desktop login session (systemd --user).

Two critical architectural invariants are visible in these structures:

  • Explicit clock injection: reconcile() accepts now: SystemTime as an explicit parameter. It never calls SystemTime::now() internally. This allows test suites to freeze time or jump across boundaries without altering system clocks or sleeping.
  • Ignored enabled flag: While Connection.enabled is copied to the final StatusRow, it is never passed into the classification logic. Health reflects physical machine reality. A disabled connection whose proxy process is running will honestly report HealthState::Running. The enabled field gates user start policy, not truthfulness of status.

The dispatcher: from reconcile() to classify()

The public entry point for the module is reconcile(). It delegates to an internal classify() function that matches on the simplified UnitState enum:

/// Classify one Connection's Health state from a single observation.
///
/// Pure: the same `identity`, `observation`, and `now` always produce the
/// same [`StatusRow`] fields (`docs/reconcile.v1.md`, "Mental model").
pub(crate) fn reconcile(
    identity: &Connection,
    observation: &Observation,
    now: SystemTime,
) -> StatusRow {
    let port_open = port_is_open(observation.port.probe);
    let classification = classify(
        &observation.unit,
        port_open,
        &observation.port,
        now,
        identity.port,
    );

    StatusRow {
        id: identity.id.clone(),
        name: identity.name.clone(),
        group: identity.group.clone(),
        instance: identity.instance.clone(),
        address: identity.address.clone(),
        port: identity.port,
        private_ip: identity.private_ip,
        enabled: identity.enabled,
        state: classification.state,
        source: classification.source,
        pid: classification.pid,
        unit: model::unit_name(&identity.id).ok(),
        port_open,
        uptime_sec: classification.uptime_sec,
        error: classification.error,
    }
}

classify() cleanly separates computing the core trio (HealthState, Source, Option<StatusError>) from attributing process details like pid and uptime_sec:

fn classify(
    unit: &UnitObservation,
    port_open: bool,
    port: &PortObservation,
    now: SystemTime,
    port_number: u16,
) -> Classification {
    let outcome = match unit.state {
        UnitState::Idle => classify_inactive(port_open, port, port_number),
        UnitState::Activating => classify_activating(unit, port_open, port, now, port_number),
        UnitState::Active => classify_active(unit, port_open, port, now, port_number),
        UnitState::Deactivating => classify_deactivating(unit, port_open),
        UnitState::Failed(signal) => classify_failed(signal, unit, port_open),
    };

    // `pid`/`uptime_sec` are only reported for a process we attribute to our
    // Unit (`docs/reconcile.v1.md`, "Outputs (Status row)": "when known and
    // relevant").
    let pid = if outcome.source == Source::Unit {
        unit.main_pid
    } else {
        None
    };
    let uptime_sec = if outcome.source == Source::Unit {
        uptime_since(unit.started_at, now)
    } else {
        None
    };

    Classification {
        state: outcome.state,
        source: outcome.source,
        pid,
        uptime_sec,
        error: outcome.error,
    }
}

The start window and two independent clocks

How can a stateless CLI tell whether a service with a closed port is legitimately starting up or permanently stuck, without maintaining a persistent state file on disk?

The answer is START_WINDOW. When systemd launches a unit, it records a monotonic start timestamp (ExecMainStartTimestamp). By comparing this timestamp against the observation time now, Reconcile can determine how long the unit has been attempting to start:

/// The start window (`docs/reconcile.v1.md`, "Start window"): a Connection
/// stays `starting` for at most this long after a start attempt before
/// Reconcile calls it `start_timeout` / `unit_failed` instead. Same numeric
/// default as the CLI's `--wait-ms` (`docs/cli-contract.v1.md`), but that
/// flag only bounds how long a command *blocks*; this constant is what
/// Reconcile itself uses on every call, including plain `status`.
pub(crate) const START_WINDOW: Duration = Duration::from_millis(10_000);

fn within_start_window(started_at: Option, now: SystemTime) -> bool {
    match started_at {
        None => false,
        Some(t) => age_since(t, now) <= START_WINDOW,
    }
}

Trap: Two Independent Clocks

Do not confuse Reconcile's START_WINDOW with the CLI flag --wait-ms:

  • START_WINDOW (10s): A pure classification window used by reconcile() on every single status observation to decide whether a closed port is Starting vs Error (start_timeout / unit_failed).
  • --wait-ms (default 10s): An I/O loop budget in the CLI start and restart commands that controls how long the command blocks polling until status reaches Running.

The mutation loop must never abort early just because a single intermediate poll returned Reconcile's start_timeout. As long as time remains on the caller's --wait-ms budget, the loop continues polling.

Notice also the handling of missing timestamps: if started_at is None, within_start_window returns false. An undated connection is never assumed to be "just started," preventing stuck units from being trapped in eternal Starting status.

Clean stops vs. real failures

When an operator stops a service, systemd sends a SIGTERM. Depending on how the process exits and whether systemd's reset-failed has run, systemd may classify the unit as ActiveState=failed. If a control plane treated every ActiveState=failed as an error, a cleanly stopped proxy would appear broken to the user.

To prevent this, cloud-sql-tracker configures all proxy units with the flag --exit-zero-on-sigterm. When stopped gracefully, the proxy exits with code 0. Reconcile then inspects the failure signal and recognizes three distinct clean stop branches:

/// Whether a failed Unit's raw signal matches a clean stop, an exec
/// failure, or a crash (`docs/reconcile.v1.md`, "Clean stop vs failed
/// unit"). `ExecMainCode` (exited vs killed) is not modeled: the doc calls
/// the `Result`/`ExecMainStatus` pairs below "sufficient when in doubt".
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum FailureKind {
    /// Never reached a steady running process.
    ExecFailed,
    /// Crash, unexpected nonzero exit, SIGKILL, stop-timeout, or OOM.
    Crashed,
    /// Branch A, B, or C of "Clean stop vs failed unit".
    CleanStop,
}

fn classify_failure_signal(signal: FailureSignal) -> FailureKind {
    use UnitResult::*;

    match (signal.result, signal.exec_main_status) {
        // Branch A: proxy honored --exit-zero-on-sigterm.
        (Success, _) => FailureKind::CleanStop,
        (ExitCode, 0) => FailureKind::CleanStop,
        // Branch B: killed by the default KillSignal (SIGTERM = 15).
        (Signal, 15) => FailureKind::CleanStop,
        // Branch C: exited 143 (128 + SIGTERM) after SIGTERM.
        (ExitCode, 143) => FailureKind::CleanStop,
        (ExecCondition, _) => FailureKind::ExecFailed,
        // SIGKILL (9), stop timeout, OOM/core-dump, or any other nonzero
        // exit / signal: a real crash, not a clean stop.
        (Signal, _) | (Timeout, _) | (CoreDump, _) | (ExitCode, _) => FailureKind::Crashed,
    }
}

Why SIGKILL is Never Clean

Notice that SIGKILL (signal 9) is strictly categorized under FailureKind::Crashed. A clean stop uses SIGTERM. Receiving SIGKILL indicates that the process failed to shut down before systemd's stop timeout expired, or that an external administrator manually killed the process with kill -9.

If a unit has FailureKind::CleanStop, the port is closed, and no live PID remains, classify_failed returns HealthState::Stopped with no error attached:

fn classify_failed(signal: FailureSignal, unit: &UnitObservation, port_open: bool) -> Outcome {
    let kind = classify_failure_signal(signal);

    if kind == FailureKind::CleanStop && !port_open && unit.main_pid.is_none() {
        // Our own `--exit-zero-on-sigterm` stop pattern, port closed, no
        // live process left: a clean stop, not a failure.
        return Outcome {
            state: HealthState::Stopped,
            source: Source::None,
            error: None,
        };
    }
    // ...
}

Foreign processes, listener matching, and unreachable probes

Reconcile enforces strict rules around network sockets and process ownership.

PID attribution and foreign processes

When a port is open, Reconcile compares the socket's listener PID with the systemd unit's MainPID:

/// `docs/reconcile.v1.md`, "PID attribution": an observed port holder is
/// consistent with our Unit owning the port when no other holder is known,
/// or the known holder is our Unit's `MainPID`.
fn listener_matches_unit(main_pid: Option<u32>, listener_pid: Option<u32>) -> bool {
    match listener_pid {
        None => true,
        Some(pid) => Some(pid) == main_pid,
    }
}

src/reconcile.rs:409–414

If another process (such as a local Docker container or an orphaned proxy started outside of systemd) holds the port, Reconcile immediately returns HealthState::Error with error code port_in_use. In accordance with ADR 0003, v1 does not adopt orphan processes. An unmanaged proxy on our port is a foreign collision that the operator must resolve.

Unreachable port probes

When probing TCP ports, connection attempts can occasionally time out or be rejected. Reconcile maps probe results conservatively:

/// `docs/reconcile.v1.md`, "`port_open` mapping": only an `Open` probe
/// counts. `Unreachable` (timeout / filtered) is treated the same as
/// `Closed` — rare on loopback, and v1 does not add a third Health path
/// for it.
fn port_is_open(probe: PortProbe) -> bool {
    matches!(probe, PortProbe::Open)
}

src/reconcile.rs:420–422

On loopback (127.0.0.1), unreachable probes are rare. Mapping Unreachable to false ensures that transient network hiccups are treated as closed rather than falsely reporting that a healthy service is listening.

Pinned invariants in unit tests

Because src/reconcile.rs is pure and decoupled from system I/O, its test suite can exercise complex edge cases in microseconds without spawning processes or setting up mock frameworks. Let us examine two actual test cases from the module:

1. Detecting port conflicts on active units

What happens if our systemd unit is active (PID 111), but another process (PID 222, docker-proxy) binds to the port first?

#[test]
fn active_with_open_port_and_mismatched_listener_is_a_port_conflict() {
    let unit = unit_with(UnitState::Active, Some(111), Some(now()));
    let port = port_with(PortProbe::Open, Some(222), Some("docker-proxy"));
    let row = reconcile(&connection("fe-dev", 15432), &observe(unit, port), now());
    assert_eq!(row.state, HealthState::Error);
    assert_eq!(row.source, Source::Unit);
    // Source stays Unit even though the port belongs to someone else —
    // unlike the idle-unit case, our Unit is genuinely active.
    assert_eq!(row.pid, Some(111));
    assert_eq!(row.error.unwrap().code, ErrorCode::PortInUse);
}

2. Recognizing clean stops under failed unit states

What happens if systemd leaves a unit in ActiveState=failed after a normal shutdown?

#[test]
fn failed_unit_with_a_clean_stop_signal_and_no_process_is_stopped() {
    let signal = FailureSignal {
        result: UnitResult::Success,
        exec_main_status: 0,

    let unit = unit_with(UnitState::Failed(signal), None, None);

    assert_eq!(row.source, Source::None);
    assert_eq!(row.error, None);
}

Check yourself

  1. Why does within_start_window treat a None start timestamp as outside the start window rather than assuming the service just started?
    Answer

    Treating a missing timestamp as inside the start window would cause an undated or stuck connection to report Starting forever. Defaulting to outside the window ensures it promptly fails with a timeout or unit failure.

  2. How do Reconcile's START_WINDOW and the CLI's --wait-ms differ in their responsibilities, and why are they independent clocks?
    Answer

    START_WINDOW (10s) is a pure classification rule deciding whether an observed closed port is still in its startup grace period. --wait-ms is an I/O polling budget controlling how long the CLI command blocks waiting for Running.

  3. Why are there three separate clean-stop branches in classify_failure_signal, and why is SIGKILL (signal 9) excluded from all of them?
    Answer

    Systemd and proxies report SIGTERM stops differently depending on flags and signal trapping (exit code 0, raw signal 15, or exit code 143). SIGKILL is excluded because it indicates an ungraceful kill or stop-timeout, which represents an abnormal termination.
