Chapter 08 · Part III

Three smaller adapters

Discover how cloud-sql-tracker interacts with the host OS without heavyweight frameworks: probing ports with procfs, discovering binaries and credentials, running bounded subprocesses, and streaming systemd journals.

In Chapter 07, we saw how the supervisor adapter speaks D-Bus directly to systemd --user. But a full control plane requires three additional interactions with the Linux environment:

  1. Port observation: Checking if a local TCP port is open and discovering which process owns it (procfs).
  2. Environment discovery: Finding the cloud-sql-proxy executable on PATH and validating Application Default Credentials.
  3. Bounded subprocess execution & journal streaming: Probing proxy version identity without hanging, and reading structured logs from journalctl.
Why

Per ADR 0004, cloud-sql-tracker prefers direct, native Linux interfaces over scraping shell pipelines like ss or pgrep. Small, dedicated adapters isolate operating system I/O behind narrow boundaries, ensuring that higher-level decision logic remains pure and deterministic.

1. Port observation and listener attribution (src/port.rs)

When Reconcile evaluates a Connection, it needs to know whether the configured local TCP port (e.g. 127.0.0.1:15432) is open. But a simple boolean "is the port open?" is dangerously incomplete. If port 15432 is open, who is holding it? Is it our managed Unit's PID, or is it an unmanaged Foreign process like Docker or a manual proxy?

The port module answers both questions via a single public entry point: observe().

pub(crate) fn observe(address: IpAddr, port: u16) -> PortObservation {
    let probe = probe_tcp(address, port);
    let (listener_pid, listener_name) = attribute_listener(address, port);
    PortObservation {
        probe,
        listener_pid,
        listener_name,
    }
}

The authoritative TCP liveness probe

Liveness is verified by attempting a real TCP connection with a strict 200 millisecond timeout:

const CONNECT_TIMEOUT: Duration = Duration::from_millis(200);

fn probe_tcp(address: IpAddr, port: u16) -> PortProbe {
    match TcpStream::connect_timeout(&SocketAddr::new(address, port), CONNECT_TIMEOUT) {
        Ok(_stream) => PortProbe::Open,
        Err(err) => classify_connect_error(&err),
    }
}

fn classify_connect_error(err: &io::Error) -> PortProbe {
    if err.kind() == io::ErrorKind::ConnectionRefused {
        PortProbe::Closed
    } else {
        PortProbe::Unreachable
    }
}

src/port.rs:24–62

Pure Logic

Notice the three-way classification of PortProbe: Open (connect succeeded), Closed (explicit ECONNREFUSED from the kernel), or Unreachable (timeout, network unreachable, or firewall filter). If a connect times out, treating it as "closed" would be a false negative. Classifying it as Unreachable alerts doctor to investigate connectivity issues.

Listener attribution via procfs

If the port is listening, attribute_listener inspects Linux's /proc filesystem to discover the PID and process name. It executes a 4-step pipeline:

┌────────────────────────────────────────────────────────┐ │ 1. Scan /proc/net/tcp & /proc/net/tcp6 for LISTEN entries│ └───────────────────────────┬────────────────────────────┘ │ binds_to(local, addr, port) ▼ ┌────────────────────────────────────────────────────────┐ │ 2. Find socket inode matching address:port │ └───────────────────────────┬────────────────────────────┘ │ scan /proc/<pid>/fd/* ▼ ┌────────────────────────────────────────────────────────┐ │ 3. Attribute inode to a unique owning Process PID │ └───────────────────────────┬────────────────────────────┘ │ read /proc/<pid>/comm ▼ ┌────────────────────────────────────────────────────────┐ │ 4. Extract process command name (e.g. "cloud-sql-proxy")│ └────────────────────────────────────────────────────────┘

First, matching socket table entries must handle wildcard bindings correctly:

fn binds_to(local: SocketAddr, address: IpAddr, port: u16) -> bool {
    local.port() == port && (local.ip() == address || local.ip().is_unspecified())
}

src/port.rs:108–110

An entry listening on 0.0.0.0 or :: (is_unspecified()) binds to all network interfaces on the host, which means it occupies the Connection's specific loopback IP (127.0.0.1).

Next, the adapter scans process file descriptors to find which process owns the socket inode:

fn pid_holding_inode(inode: u64) -> Option {
    let holders = all_processes_best_effort().filter_map(|process| {
        let holds_inode = process
            .fd()
            .ok()?
            .filter_map(Result::ok)
            .any(|fd| matches!(fd.target, FDTarget::Socket(fd_inode) if fd_inode == inode));
        holds_inode.then(|| process.pid() as u32)
    });
    unique(holders)
}

src/port.rs:117–126

Defensive Attribution

Attribution is strictly best-effort and unambiguous. The unique() helper ensures that if zero processes or more than one process references the socket inode (such as during rapid process fork/exec cycles), it returns None rather than guessing. Furthermore, the process name is read directly from /proc/<pid>/comm rather than /proc/<pid>/stat, avoiding fragile string-parsing bugs when process names contain parentheses or spaces.

2. Binary and credentials discovery (src/env/mod.rs)

The env module acts as the single authority for finding the proxy executable on disk and verifying Google Cloud credentials.

Executable resolution: NotFound vs NotExecutable

When starting a proxy or running diagnostic preflights, the control plane needs to locate the binary specified in configuration (or default to cloud-sql-proxy):

pub(crate) fn resolve_proxy_bin(configured: Option<&str>) -> Result {
    let name = configured.unwrap_or(DEFAULT_PROXY_BIN);
    let path_env = std::env::var_os("PATH").unwrap_or_default();
    resolve_bin(name, &path_env)
}

fn resolve_bin(name: &str, path_env: &OsStr) -> Result {
    let candidate = Path::new(name);
    if candidate.is_absolute() {
        return require_executable_file(candidate).map(|()| candidate.to_path_buf());
    }

    let mut non_executable_match = None;
    for dir in std::env::split_paths(path_env) {
        let candidate = dir.join(name);
        if is_executable_file(&candidate) {
            return Ok(candidate);
        }
        if non_executable_match.is_none() && candidate.is_file() {
            non_executable_match = Some(candidate);
        }
    }

    match non_executable_match {
        Some(path) => Err(ProxyBinError::NotExecutable { path }),
        None => Err(ProxyBinError::NotFound {
            name: name.to_string(),
        }),
    }
}

src/env/mod.rs:37–138

Sharp Error Distinction

Notice the distinction between ProxyBinError::NotFound and ProxyBinError::NotExecutable. If a file named cloud-sql-proxy exists in a PATH directory but lacks the executable bit (0o111 permissions), reporting "not found" would confuse the operator. The resolver explicitly flags NotExecutable so the diagnostic hint instructs the user to check file permissions.

Local ADC verification

Per ADR 0002, Google Application Default Credentials (ADC) are mandatory. The env module checks for credentials using a 2-tier priority rule:

  1. Priority 1: If GOOGLE_APPLICATION_CREDENTIALS is set in the environment, that specific file path must exist and be readable.
  2. Priority 2: Otherwise, check the standard user location at ~/.config/gcloud/application_default_credentials.json.
fn resolve_adc_status(home: Option<&Path>, gac_env: Option<&Path>) -> AdcStatus {
    if let Some(path) = gac_env {
        return AdcStatus {
            present: is_readable_file(path),
            path: Some(path.to_path_buf()),
            gac_env_set: true,
        };
    }

    let default_path = home.map(|home| home.join(ADC_RELATIVE_PATH));
    AdcStatus {
        present: default_path.as_deref().is_some_and(is_readable_file),
        path: default_path,
        gac_env_set: false,
    }
}

src/env/mod.rs:239–253

Local Inspection Only

resolve_adc_status is entirely local. It checks file readability (is_readable_file) but never spawns gcloud, connects to Google servers, or verifies OAuth token validity. This guarantees that doctor runs in milliseconds and never hangs on network latency.

3. Subprocess execution & version probing (src/env/version_probe.rs)

When cloud-sql-tracker doctor validates the proxy binary, simply checking that an executable exists on PATH is insufficient—an operator might have placed an unrelated binary or broken wrapper script at that path. Doctor therefore executes cloud-sql-proxy -v to verify identity and capture the version string (e.g. 2.25.2+linux.amd64).

Critical Architectural Rule

start deliberately does NOT probe proxy versions. When starting connections, start only calls resolve_proxy_bin to obtain the path. Probing -v on every startup would add latency and redundant subprocess spawns. The version probe belongs exclusively to doctor.

The timeout problem in Rust's standard library

Rust's standard library provides Child::wait() (which blocks indefinitely) and Child::try_wait() (which checks without blocking), but has no built-in wait with timeout. If an operator configures a proxy wrapper script that waits on standard input, a standard Command::output() would hang the process forever, freezing UI widgets like the Omarchy bar.

To solve this cleanly without external crates, version_probe.rs uses a background waiter thread and an mpsc channel with recv_timeout:

fn run_proxy_version_command(path: &Path) -> Result {
    let child = spawn_version_probe(path)?;
    let pid = child.id();

    let (tx, rx) = mpsc::channel();
    std::thread::spawn(move || {
        let _ = tx.send(child.wait_with_output());
    });

    match rx.recv_timeout(PROXY_VERSION_TIMEOUT) {
        Ok(Ok(output)) => Ok(ProxyVersionOutput {
            status: output.status,
            stdout: output.stdout,
            stderr: output.stderr,
        }),
        Ok(Err(err)) => Err(ProxyVersionError::WaitFailed {
            detail: err.to_string(),
        }),
        Err(RecvTimeoutError::Timeout) => {
            terminate_version_probe(pid);
            Err(ProxyVersionError::TimedOut)
        }
        Err(RecvTimeoutError::Disconnected) => Err(ProxyVersionError::WaitFailed {
            detail: "version probe wait thread ended without a result".to_string(),
        }),
    }
}

src/env/version_probe.rs:106–149

Two critical subprocess engineering details

  1. Deadlock prevention via concurrent pipe draining: Operating system pipe buffers are typically 64 KB. If a child writes extensive output to stdout or stderr while the parent waits without reading, the child blocks on write() and deadlocks. Calling child.wait_with_output() inside the thread automatically drains both pipes concurrently.
  2. Process group termination: When spawning the child, the adapter configures .process_group(0): 
    fn spawn_version_probe(path: &Path) -> Result {
    Command::new(path)
        .arg("-v")
        .stdout(Stdio::piped())
        .stderr(Stdio::piped())
        .process_group(0)
        .spawn()
        .map_err(|err| ProxyVersionError::SpawnFailed {
            detail: err.to_string(),
        })
}

    src/env/version_probe.rs:154–164

    On timeout, terminate_version_probe kills the entire process group using kill_process_group(pid, Signal::KILL) via the rustix crate. If a wrapper shell script spawned a background child (such as sleep), killing only the top-level shell PID would leave the child running and holding open the output pipes.

Benchmark Discovery

An earlier implementation polled try_wait() inside a 20 ms sleep loop. Benchmarking showed that while cloud-sql-proxy -v executes in only ~9 ms, the 20 ms poll quantum artificially inflated doctor latency to ~48 ms. Switching to the blocking channel recv_timeout reduced doctor execution time to ~35 ms, waking up instantly upon process completion.

4. Systemd journal streaming (src/journal.rs)

When an operator runs cloud-sql-tracker logs fe-dev or doctor checks journal accessibility, the control plane needs to read logs from systemd's user journal. Rather than linking against heavy C libraries (libsystemd) or complex log-parsing crates, the adapter shells out directly to journalctl.

pub(crate) fn dump(unit: &UnitName, lines: u32) -> Result {
    let unit_arg = format!("--unit={}", unit.as_str());
    let lines_arg = lines.to_string();
    let output = run_journalctl(&[
        "--user",
        &unit_arg,
        "--no-pager",
        "--quiet",
        "-n",
        &lines_arg,
        "-o",
        "short-iso",
    ])?;
    Ok(dump_from_output(output))
}

fn dump_from_output(output: Output) -> Dump {
    if output.stdout.iter().all(u8::is_ascii_whitespace) {
        Dump::Empty
    } else {
        Dump::Bytes(output.stdout)
    }
}

src/journal.rs:63–88

Separation of concerns: Dump enum

The journal module preserves raw bytes without altering encoding:

#[derive(Debug, Clone, PartialEq, Eq)]
pub(crate) enum Dump {
    Empty,
    Bytes(Vec),
}

src/journal.rs:25–29

journal.rs does not format terminal UI messages or decide process exit codes. If dump returns Dump::Empty, the cli layer decides whether to print a human-readable hint (e.g. "no logs found for fe-dev") to stderr. If it returns Dump::Bytes, cli streams the raw output directly to stdout.

Check yourself

  1. Why does port::observe return a three-way PortProbe enum (Open, Closed, Unreachable) instead of a simple boolean is_open: bool?
    Answer

    A boolean cannot distinguish between an actively refused connection (the port is definitely closed and available) and a timeout or firewall error (unreachable). Treating timeouts as closed would produce false passes in health checks.

  2. Why does version_probe.rs configure a new process group (process_group(0)) and terminate with kill_process_group on timeout?
    Answer

    If the configured proxy executable is a shell script that launches helper subprocesses (like sleep), killing only the parent shell PID leaves helper processes alive and holding stdout/stderr pipes open, preventing clean termination.

  3. Why does cloud-sql-tracker start deliberately avoid running the version identity probe that doctor runs?
    Answer

    Startup is performance-critical and should remain fast. Running a version probe subprocess on every start invocation would add unnecessary latency, whereas start only needs to resolve the executable path to launch the transient unit.
