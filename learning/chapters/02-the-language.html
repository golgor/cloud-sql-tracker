The language

Explore the authoritative domain vocabulary of cloud-sql-tracker and see how every concept maps directly to a concrete Rust type.

Domain vocabulary as a system

In a systems control plane that coordinates Linux processes, ports, configuration files, and D-Bus interfaces, ambiguous terms cause architectural bugs. The file CONTEXT.md establishes the strict domain language of this project. Every term has a single specific meaning and maps 1:1 to a Rust struct, enum, or function.

Here is the domain glossary as an interconnected system:

Connection
Definition: One configured Cloud SQL instance plus its fixed local listen endpoint (id, name, group, instance connection name, port, and connection flags).
Why: Distinguishes static configuration intent from any running process. In code: struct Connection in src/model.rs:153.
Proxy process
Definition: An active Linux operating system process running Google's cloud-sql-proxy executable on behalf of a Connection.
Why: The proxy process is the actual data-plane runtime with an OS Process ID (PID). In code: tracked via pid: Option<u32> in src/model.rs:276.
Control plane
Definition: The short-lived cloud-sql-tracker CLI that starts, stops, reconciles, and reports on Proxy processes.
Why: Separates lifecycle supervision and status reporting from the SQL data stream. In code: the cloud_sql_tracker::cli entrypoint in src/main.rs:12.
Status document
Definition: The complete, versioned JSON snapshot of all configured Connections and their computed health returned by status --json.
Why: Provides an atomic, machine-readable contract for desktop UI widgets and automation scripts. In code: struct StatusDocument in src/model.rs:294.
Health state
Definition: One of four discrete operational states (stopped, starting, running, error) computed for a Connection at a single moment.
Why: Eliminates fuzzy status descriptions and gives UIs a deterministic four-state model. In code: enum HealthState in src/model.rs:172.
Reconcile
Definition: The pure, side-effect-free function that maps observed operating system signals (systemd state and port probes) to a Connection's Health state.
Why: Separates decision policy from Linux I/O, enabling exhaustive automated testing. In code: fn reconcile() in src/reconcile.rs:102.
Source
Definition: The process ownership provenance for a Connection's port (either unit if managed by our systemd service, or none).
Why: Disentangles process health from process ownership. In code: enum Source in src/model.rs:188.
Foreign process
Definition: Any process holding a Connection's configured local port that is not our managed systemd Unit process.
Why: Unmanaged listeners (including leftover manually run proxies or Docker containers) are classified as port conflicts (error / port_in_use), never adopted. In code: ErrorCode::PortInUse in src/model.rs:236.
Group
Definition: A logical category label assigned to Connections (such as backend, fe, or iot) for filtering and bulk start/stop operations.
Why: Allows developers to toggle entire clusters of related microservice proxies with a single command (start --group backend). In code: group: String in src/model.rs:156.
Unit
Definition: The dynamic systemd --user transient service (named cloud-sql-proxy-<id>.service) supervising a single managed Proxy process.
Why: Delegates process isolation, log capture, and clean signal termination to the Linux init system. In code: struct UnitName in src/model.rs:18.
Supervisor
Definition: The user session systemd daemon (systemd --user) communicating over D-Bus.
Why: Serves as the actual long-lived process supervisor on Linux. In code: src/supervisor.rs.

Concepts newcomers easily conflate

When studying this codebase, two distinctions are critical to avoid confusion:

1. Connection vs. Proxy process vs. Unit

┌──────────────────────────────────────────────────────────┐ │ Connection (Configuration entity in connections.json) │ │ id: "fe-dev", port: 15434, instance: "proj:region:inst" │ └────────────────────────────┬─────────────────────────────┘ │ Managed by systemd ▼ ┌──────────────────────────────────────────────────────────┐ │ Unit (Transient systemd service) │ │ Name: "cloud-sql-proxy-fe-dev.service" │ └────────────────────────────┬─────────────────────────────┘ │ Spawns & monitors ▼ ┌──────────────────────────────────────────────────────────┐ │ Proxy process (Operating system process running binary) │ │ Command: /usr/bin/cloud-sql-proxy ... (PID: 12450) │ └──────────────────────────────────────────────────────────┘

These three represent three distinct layers of existence:

  • A Connection always exists as long as it is listed in connections.json, even when completely stopped.
  • A Unit only exists in systemd when the service is starting, active, or in a failed state.
  • A Proxy process is the physical OS process executing CPU instructions and holding a TCP socket.

2. Health state vs. Source

Newcomers often assume that if a local port is accepting TCP connections, the Connection must be in the running state. This is false. HealthState and Source are orthogonal dimensions:

Local Port 15434 Unit Main PID HealthState Source Meaning
Accepting TCP Matches Listener PID running unit Healthy managed proxy running normally.
Closed None (Inactive) stopped none Cleanly stopped connection.
Accepting TCP No Unit / Wrong PID error none Port conflict! A foreign process (e.g. Docker or rogue proxy) holds the port.
Closed Active Unit (within 10s) starting unit Unit recently launched; waiting for proxy to bind port.
Trap

v1 never adopts orphan processes. If someone starts cloud-sql-proxy manually in a terminal tab on port 15434, cloud-sql-tracker will not claim ownership of it. It classifies the connection as state: error with error.code: port_in_use and source: none.

2. HealthState and Source

/// A Connection's health, produced by Reconcile (`docs/reconcile.v1.md`).
///
/// Serializes to the Status document's lowercase `state` strings
/// (`docs/status-document.v1.md`, "`state` (Health state)").
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize)]
#[serde(rename_all = "lowercase")]
pub(crate) enum HealthState {
    Stopped,
    Starting,
    Running,
    Error,
}

/// Process ownership signal, orthogonal to [`HealthState`].
///
/// Only `unit` | `none` in v1 — there is no `orphan` Source
/// (`CONTEXT.md`, "Source"; `docs/status-document.v1.md`, "source").
///
/// Serializes to the Status document's lowercase `source` strings
/// (`docs/status-document.v1.md`, "`source` (ownership)").
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize)]
#[serde(rename_all = "lowercase")]
pub(crate) enum Source {
    /// Process is the MainPID of our expected user Unit.
    Unit,
    /// No managed Unit process attributed.
    None,
}

Check yourself

  1. What is the fundamental difference between a Connection, a Unit, and a Proxy process?
    Answer

    A Connection is static configuration data in JSON, a Unit is systemd's transient service wrapper, and a Proxy process is the running OS executable with a physical process ID.

  2. Why are Health state and Source represented as two separate fields on a StatusRow rather than a single combined enum?
    Answer

    They are orthogonal concepts: Health state describes whether the local endpoint accepts connections, while Source indicates whether that listener is owned by our managed systemd unit or unmanaged.

  3. What is a Foreign process, and why does the v1 control plane refuse to adopt it into an active Source?
    Answer

    A Foreign process is any unmanaged process holding a configured port; adopting it would create subtle process lifecycle bugs and hide port conflicts caused by rogue processes or local containers.
