Chapter 10 · Part IV

The thin shell

Explore the outermost CLI presentation layer: how cloud-sql-tracker parses arguments with clap in exactly one module, maps batch execution outcomes to a strict exit-code contract, and formats human text versus machine JSON.

In Chapter 09, we explored the commands seam: the typed engine that drives all application behavior without parsing arguments or printing to the screen. Now we reach the edge of the binary: src/cli.rs and src/main.rs.

cli.rs is the only module in the entire crate permitted to:

  1. Import and derive types from the clap library.
  2. Read process arguments via std::env::args().
  3. Print formatted human text or JSON to stdout and stderr.
  4. Determine the operating system process exit code (0, 1, 2, 3, or 4).
┌────────────────────────────────────────────────────────┐ │ main.rs │ │ std::process::exit(cli::run()) │ └───────────────────────────┬────────────────────────────┘ │ (no argv parameter!) ▼ ┌────────────────────────────────────────────────────────┐ │ cli.rs │ │ - clap parsing (Cli, SelectorArgs, Commands) │ │ - resolve_selector() (pure exclusivity & defaults) │ │ - exit_for_batch() (outcome -> exit code 0..4) │ │ - format status / doctor / logs / errors │ └───────────────────────────┬────────────────────────────┘ │ typed structs (Selector, wait_ms) ▼ ┌────────────────────────────────────────────────────────┐ │ commands seam │ └────────────────────────────────────────────────────────┘

1. A thirteen-line main.rs

Because all argument parsing, execution routing, and exit code selection live in cli.rs, the binary's entry point is stripped of all logic:

fn main() {
    std::process::exit(cloud_sql_tracker::cli::run());
}

src/main.rs:11–13

Why cli::run() Takes No Arguments

Notice that cli::run() takes no arguments. It reads std::env::args() directly inside the function. Integration tests in tests/cli_smoke.rs and tests/cli_json_contracts.rs do not test by calling library functions with mock strings; they spawn the real compiled binary on disk using std::process::Command. Keeping main.rs trivial ensures that binary test runs execute identical code to production invocations.

2. The bare version flag challenge

Per docs/cli-contract.v1.md, running cloud-sql-tracker --version or -V must print a bare semantic version string (e.g. 0.1.1), with no binary name prefix, no v prefix, and no trailing whitespace.

However, clap's built-in #[command(version)] handler unconditionally formats output as "{bin_name} {version}" (e.g. cloud-sql-tracker 0.1.1). In clap_builder 4.6, there is no template hook to suppress the binary name.

cloud-sql-tracker solves this by disabling clap's built-in version flag and declaring a manual boolean flag:

#[derive(Debug, Parser)]
#[command(name = "cloud-sql-tracker", disable_version_flag = true)]
struct Cli {
    /// Config file override. Default: $XDG_CONFIG_HOME/cloud-sql-tracker/connections.json
    #[arg(long = "config", value_name = "PATH")]
    config: Option,

    /// Print the bare version and exit.
    #[arg(short = 'V', long = "version")]
    version: bool,

    #[command(subcommand)]
    command: Option,
}

src/cli.rs:55–71

When cli.version is true, run() immediately outputs the compile-time crate version and exits 0:

pub fn run() -> i32 {
    let cli = Cli::parse();

3. Selector resolution and exclusivity (resolve_selector)

Subcommands like start, stop, and status accept target selectors: an ID positional argument, --group <NAME>, or --all. Rather than relying on clap's ArgGroup attribute (which hides validation inside macro-generated code), cli.rs validates selectors using a pure function:

fn resolve_selector(
    args: SelectorArgs,
    require_target: bool,
) -> Result {
    let provided = [args.id.is_some(), args.group.is_some(), args.all]
        .into_iter()
        .filter(|set| *set)
        .count();
    if provided > 1 {
        return Err(UsageError(
            "id, --group, and --all cannot combine (docs/cli-contract.v1.md, \
             \"Target selectors\": \"Mutual exclusion\")"
                .to_string(),
        ));
    }

    if let Some(id) = args.id {
        return Ok(commands::Selector::Id(id));
    }
    if let Some(group) = args.group {
        return Ok(commands::Selector::Group(group));
    }
    if args.all {
        return Ok(commands::Selector::All);
    }

    if require_target {
        return Err(UsageError(
            "an explicit target is required: ID, --group NAME, or --all \
             (docs/cli-contract.v1.md, \"Target selectors\": \"Defaults\")"
                .to_string(),
        ));
    }
    Ok(commands::Selector::All)
}

src/cli.rs:196–233

Pure Logic

This design provides two major benefits:

  1. Fast unit testing: Unit tests in src/cli.rs test mutual exclusion and default fallback directly across 8 separate test cases without spawning subprocesses or parsing fake CLI argv strings.
  2. Subcommand-specific defaults: For status, an omitted selector defaults to Selector::All (require_target: false). For mutating commands (start, stop, restart), an omitted selector is rejected with exit code 2 (require_target: true).

4. The exit code contract (0–4)

Command-line automation and desktop UI widgets depend on deterministic, machine-interpretable process exit codes. The exit code contract is frozen in docs/cli-contract.v1.md:

Code Name Meaning Example Scenarios
0 Success All requested operations succeeded or were idempotent no-ops; status produced a document; restart --failed with no failed units; logs succeeded (even if journal was empty). start --all (7/7 ok)
status --json (even with error rows)
logs fe-dev
1 Partial Failure Multi-target batch where at least one target succeeded and at least one failed. Survivors remain running. Never used by single-id commands or logs. start --all (6 started ok, 1 port conflict)
2 Usage / Config Invalid CLI arguments, syntax errors, missing/unreadable config file, unknown connection ID or group name, target mutual exclusion violation, single-id start on disabled connection. start nope
start fe-dev --all
logs --lines 0
3 Dependency Environmental prerequisite failure: systemd user D-Bus unreachable, proxy_bin binary not found on PATH, journalctl binary missing, or any doctor preflight check failed. start --all (no systemd session)
doctor (ADC missing)
logs (no journalctl)
4 Total Failure Every attempted target in a batch failed, or a single-id mutating command failed after attempting the operation. Never used by logs. start --all (0/7 ok)
start fe-dev (crashed or port in use)

Mapping batches to exit codes (exit_for_batch)

When a mutating command finishes, commands::mutate returns a BatchOutcome containing individual TargetResult values. cli.rs turns this outcome into a single process exit code:

fn exit_for_batch(outcome: &BatchOutcome) -> i32 {
    let refused_disabled = outcome
        .targets
        .iter()
        .any(|target| target.result == TargetResult::RefusedDisabled);
    if refused_disabled {
        return 2;
    }

    if outcome.dependency_count() > 0 {
        return 3;
    }

    if outcome.failed_count() == 0 {
        return 0;
    }

    if outcome.succeeded_count() > 0 {
        1
    } else {
        4
    }
}

src/cli.rs:384–408

Precedence Rules

Notice the exact priority order in exit_for_batch:

  1. Refused disabled target: If a single-target command targeted a disabled connection, exit 2 (usage error).
  2. Dependency failure takes precedence: If any target encountered a systemic dependency failure (like D-Bus bus down), exit 3 wins immediately—even if other connections in the batch had already started!
  3. Clean successes: If zero targets failed, exit 0.
  4. Partial vs total failure: If at least one target succeeded, exit 1; if zero targets succeeded, exit 4.

5. Human text vs machine JSON formatting

The CLI is designed to serve both humans in interactive terminals and automated UI plugins like the Omarchy bar widget.

Presentation labels decoupled from domain models

In Rust, it is tempting to implement std::fmt::Display directly on domain enums like HealthState or ErrorCode. However, cloud-sql-tracker keeps domain models in src/model.rs completely free of presentation logic. Human-readable label functions live exclusively inside src/cli.rs:

fn state_label(state: HealthState) -> &'static str {
    match state {
        HealthState::Stopped => "stopped",
        HealthState::Starting => "starting",
        HealthState::Running => "running",
        HealthState::Error => "error",
    }
}

fn error_code_label(code: ErrorCode) -> &'static str {
    match code {
        ErrorCode::BinMissing => "bin_missing",
        ErrorCode::PortInUse => "port_in_use",
        ErrorCode::ExecFailed => "exec_failed",
        ErrorCode::UnitFailed => "unit_failed",
        ErrorCode::StartTimeout => "start_timeout",
        ErrorCode::Auth => "auth",
        ErrorCode::Config => "config",
        ErrorCode::Unknown => "unknown",
    }
}

Doctor formatting

When running doctor in human mode, each check outputs a bracketed status tag ([PASS], [WARN], [FAIL]) followed by the check identifier, details, and optional recovery hints:

fn print_doctor(report: &DoctorReport, json: bool) {
    if json {
        let text = serde_json::to_string_pretty(report).expect("DoctorReport always serializes");
        println!("{text}");
        return;
    }

    for check in &report.checks {
        let status = match check.status {
            CheckStatus::Pass => "PASS",
            CheckStatus::Warn => "WARN",
            CheckStatus::Fail => "FAIL",
        };
        match &check.hint {
            Some(hint) => println!("[{status}] {}: {} (hint: {hint})", check.id, check.detail),
            None => println!("[{status}] {}: {}", check.id, check.detail),
        }
    }
    println!("{}", if report.ok { "ok" } else { "FAILED" });
}

When --json is passed, print_doctor bypasses text formatting entirely and streams the pretty-printed JSON schema document directly to stdout.

Check yourself

  1. Why does exit_for_batch return exit code 3 (Dependency) if any target encounters a dependency failure, even if several other connections started successfully?
    Answer

    A dependency failure indicates a systemic infrastructure breakdown (such as D-Bus user session loss or missing proxy binaries) rather than an individual database issue. Per the CLI contract, environmental failures take priority so automated scripts can distinguish host configuration errors from routine database failures.

  2. Why does cloud-sql-tracker disable clap's built-in #[command(version)] and handle -V/--version manually?
    Answer

    The CLI contract requires --version to output a bare semantic version string (such as 0.1.1) without a binary name or prefix. Clap's built-in version flag always prints "cloud-sql-tracker 0.1.1", and clap_builder provides no template option to remove the binary name.

  3. Why are presentation labels like state_label and error_code_label defined in src/cli.rs rather than implementing Display on types in src/model.rs?
    Answer

    model.rs defines the pure domain vocabulary and serialization structures shared across the entire crate. Text formatting for terminal output is an outermost presentation concern belonging strictly to the CLI shell, keeping domain models clean and free of UI logic.
