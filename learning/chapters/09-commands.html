Chapter 09 · Part IV

The commands seam

Discover the application logic layer: how cloud-sql-tracker orchestrates pure reconciliation with operating system adapters, manages multi-target lifecycle batches without transactional rollback, and keeps the entire domain independent of command-line argument parsing.

In Parts II and III, we examined the building blocks: the pure Reconcile decision engine and the low-level operating system adapters (Supervisor D-Bus, Port TCP/procfs, ADC discovery, and Journal streaming). Now we step up one layer into src/commands/.

The commands module is the one public business logic seam of the library crate. It coordinates what the program can actually do: query status, start proxies, stop proxies, restart proxies, run doctor diagnostics, and view logs.

┌────────────────────────────────────────────────────────┐ │ cli (clap argv & formatting) │ └───────────────────────────┬────────────────────────────┘ │ typed structs (Selector, wait_ms) ▼ ┌────────────────────────────────────────────────────────┐ │ commands seam │ │ select.rs │ status.rs │ mutate.rs │ doctor.rs │ logs.rs │ └─────────────┬───────────────────────────┬──────────────┘ │ │ ▼ ▼ ┌───────────────────────────┐ ┌────────────────────────┐ │ reconcile (pure) │ │ adapters (I/O) │ │ Decision truth table │ │ supervisor, port, env │ └───────────────────────────┘ └────────────────────────┘
Why

Per docs/modules.v1.md, the dependency direction is strictly acyclic: cli calls commands; commands calls reconcile and adapters; adapters and reconcile never call commands. Furthermore, commands contains zero clap types, zero println! or eprintln! statements, and zero exit code logic. It operates entirely on domain structs and returns typed results.

2. Target selection and error filtering (src/commands/select.rs)

Most subcommands operate on one or more Connections. The CLI parses arguments like fe-dev, --group fe, or --all into a typed Selector enum:

#[derive(Debug, Clone, PartialEq, Eq)]
pub(crate) enum Selector {
    /// Every connection in the config document, in config order.
    All,
    /// A single connection id.
    Id(String),
    /// Every connection in one group, in config order.
    Group(String),
}

src/commands/select.rs:19–27

The expand function resolves a Selector against a loaded Config. Crucially, expand is a pure function and always preserves configuration file order:

pub(crate) fn expand<'a>(
    config: &'a Config,
    selector: &Selector,
) -> Result, SelectError> {
    match selector {
        Selector::All => Ok(config.connections.iter().collect()),
        Selector::Id(id) => config::by_id(config, id)
            .map(|connection| vec![connection])
            .ok_or_else(|| SelectError::UnknownId(id.clone())),
        Selector::Group(group) => {
            let matches: Vec<&Connection> = config
                .connections
                .iter()
                .filter(|connection| &connection.group == group)
                .collect();
            if matches.is_empty() {
                Err(SelectError::UnknownGroup(group.clone()))
            } else {
                Ok(matches)
            }
        }
    }
}

src/commands/select.rs:43–64

Disabled Connections

Notice that expand() intentionally includes disabled connections (enabled: false). The status command must report on all configured connections. Mutating commands (like start) apply their own disabled-skipping policy on top of this expanded list.

For restart --failed, select.rs provides a pure filter function:

pub(crate) fn filter_failed(rows: &[StatusRow]) -> Vec<&StatusRow> {
    rows.iter()
        .filter(|row| row.state == HealthState::Error)
        .collect()
}

src/commands/select.rs:72–76

--failed is an error-state filter over already-reconciled rows, not a fourth selector variant. If no connections are currently in error, the filter returns an empty slice, which is a successful no-op rather than an error.

3. Querying system status (src/commands/status.rs)

The status command queries the state of the system and builds a canonical Status document. For each selected Connection, it performs a complete round trip:

  1. Inspects systemd D-Bus for the transient Unit state (supervisor::show).
  2. Probes the local TCP port and inspects procfs (port::observe).
  3. Combines both into a reconcile::Observation.
  4. Passes the observation into pure reconcile::reconcile() to compute the Health state.
pub(crate) fn status(
    config: &Config,
    selector: &Selector,
) -> Result {
    let targets = select::expand(config, selector)?;
    let now = SystemTime::now();
    let mono_now_usec = monotonic_now_usec();

    let mut rows = Vec::with_capacity(targets.len());
    for connection in targets {
        rows.push(observe_and_reconcile(connection, now, mono_now_usec)?);
    }

    Ok(assemble_document(
        rows,
        now,
        env!("CARGO_PKG_VERSION").to_string(),
    ))
}

Monotonic clocks and start timestamps

When systemd launches a unit, it records the start timestamp as monotonic microseconds since boot (ExecMainStartTimestampMonotonic). To calculate human-readable start times (started_at) and uptime (uptime_sec), status.rs reads the kernel's monotonic clock using rustix:

pub(super) fn monotonic_now_usec() -> Option {
    let now = rustix::time::clock_gettime(rustix::time::ClockId::Monotonic);
    let sec_usec = u64::try_from(now.tv_sec).ok()?.checked_mul(1_000_000)?;
    let nsec_usec = u64::try_from(now.tv_nsec).ok()? / 1_000;
    sec_usec.checked_add(nsec_usec)
}

fn started_at_from_monotonic(
    start_usec: u64,
    now_usec: u64,
    now: SystemTime,
) -> Option {
    let age_usec = now_usec.checked_sub(start_usec)?;
    now.checked_sub(Duration::from_micros(age_usec))
}

src/commands/status.rs:313–345

Clock Drift Trap

Why not read /proc/uptime? /proc/uptime measures CLOCK_BOOTTIME, which continues ticking while a machine is suspended. Systemd's ExecMainStartTimestampMonotonic uses CLOCK_MONOTONIC, which pauses during suspend. Using /proc/uptime on a laptop would cause calculated uptimes to drift by the cumulative suspend time! Reading ClockId::Monotonic via rustix guarantees clock domain alignment.

RFC 3339 formatting without external dependencies

The top-level Status document requires an ISO/RFC 3339 UTC timestamp (e.g. 2026-08-23T19:30:00Z). Rather than pulling in a heavy datetime crate like chrono or time, status.rs implements Howard Hinnant's famous civil_from_days algorithm:

fn format_rfc3339(now: SystemTime) -> String {
    let total_secs = now
        .duration_since(SystemTime::UNIX_EPOCH)
        .unwrap_or(Duration::ZERO)
        .as_secs();
    let days = (total_secs / 86_400) as i64;
    let secs_of_day = total_secs % 86_400;
    let (year, month, day) = civil_from_days(days);
    let hour = secs_of_day / 3_600;
    let minute = (secs_of_day % 3_600) / 60;
    let second = secs_of_day % 60;
    format!("{year:04}-{month:02}-{day:02}T{hour:02}:{minute:02}:{second:02}Z")
}

4. Mutating operations: start, stop, and restart (src/commands/mutate.rs)

Mutating operations alter the state of systemd units. They adhere to several strict architectural principles:

Non-transactional batch execution

If you run cloud-sql-tracker start --all across 7 databases, each Connection is attempted independently. If connection 4 fails due to an invalid project ID, connections 1, 2, 3, 5, 6, and 7 remain running. There is no rollback. The operation returns a BatchOutcome detailing each target's individual result.

#[derive(Debug, Clone, PartialEq, Eq)]
pub(crate) enum TargetResult {
    /// The operation succeeded, including an idempotent no-op.
    Succeeded,
    /// Skipped during --group/--all because enabled: false.
    SkippedDisabled,
    /// A single-id start/restart targeted a disabled Connection (exit 2).
    RefusedDisabled,
    /// Operation attempted and failed (e.g. port conflict, crash).
    Failed { code: ErrorCode, message: String },
    /// Systemic failure: could not reach D-Bus or resolve proxy binary.
    Dependency { message: String },
}

src/commands/mutate.rs:39–68

Idempotency

Running start on a Connection that is already running via our Unit is a success no-op. Running stop on a Connection that is already stopped is likewise a success no-op. No redundant D-Bus commands are issued.

Disabled connection policy

  • Single-ID target: Running start backend-dev when backend-dev has enabled: false is immediately refused as a usage error (TargetResult::RefusedDisabled, mapped to exit code 2).
  • Multi-target selector: Running start --group backend silently skips disabled connections (TargetResult::SkippedDisabled), printing a warning on stderr without failing the batch.

Safe unit recreation during restart

When restarting a proxy, why can't we immediately call StartTransientUnit as soon as Reconcile reports Stopped? Because systemd may still have the unit loaded in memory in a deactivating state. Issuing a new StartTransientUnit for a loaded unit causes a D-Bus UnitExists error.

Therefore, mutate.rs enforces unit_safely_recreatable():

fn unit_safely_recreatable(snapshot: &UnitSnapshot) -> bool {
    matches!(snapshot, UnitSnapshot::Absent)
}

src/commands/mutate.rs:426–428

The restart sequence stops the unit, polls until systemd has completely unloaded it (UnitSnapshot::Absent), and only then submits the new transient unit definition.

The two clocks: start-window vs wait-ms

Critical Concept

There are two completely independent clocks in cloud-sql-tracker:

  • Reconcile START_WINDOW (10s): Classifies a single instantaneous observation. If a unit is activating and its port is closed after 10s, Reconcile labels that snapshot as ErrorCode::StartTimeout.
  • CLI --wait-ms (default 10s): The total time the operator allows start or restart to poll until the proxy starts listening.

A single poll might return Reconcile's start_timeout (e.g. if the proxy took 10.1s to authorize with GCP), but if --wait-ms 30000 was requested, the CLI must not abort early! It must continue polling until the port opens or --wait-ms expires.

This is implemented in wait_step, which distinguishes permanent errors (like port conflicts) from transient start timeouts:

fn is_permanent_start_failure(code: ErrorCode) -> bool {
    matches!(
        code,
        ErrorCode::PortInUse
            | ErrorCode::ExecFailed
            | ErrorCode::Auth
            | ErrorCode::Config
            | ErrorCode::BinMissing
    )
}

fn wait_step(
    row: &StatusRow,
    is_done: &impl Fn(&StatusRow) -> bool,
    remaining: Duration,
    wait_ms: u64,
    id: &str,
    timeout_code: ErrorCode,
) -> Option {
    if is_done(row) {
        return Some(TargetResult::Succeeded);
    }
    if let Some(result) = permanent_start_failure(row) {
        return Some(result);
    }
    if remaining.is_zero() {
        if let Some(error) = row.error.as_ref() {
            return Some(TargetResult::Failed {
                code: error.code,
                message: error.detail.clone(),
            });
        }
        return Some(TargetResult::Failed {
            code: timeout_code,
            message: format!("connection `{id}` did not confirm within {wait_ms}ms"),
        });
    }
    None
}

5. Diagnostics and logs (src/commands/doctor.rs, src/commands/logs.rs)

Doctor: never fail-fast

Unlike other commands, doctor must provide a comprehensive preflight checklist even if the configuration file is completely missing or malformed:

pub(crate) fn doctor(cfg_path: &Path) -> DoctorReport {
    let loaded = config::load(cfg_path);
    let config = loaded.as_ref().ok();

    let checks = vec![
        config_check(cfg_path, &loaded),
        env::proxy_bin_check(config.map(|config| config.proxy_bin.as_str())),
        supervisor::systemd_user_check(),
        env::adc_check(),
        journal::journal_user_check(),
        ports_check(config),
    ];
    let ok = all_checks_ok(&checks);

    DoctorReport {
        version: 1,
        cli_version: env!("CARGO_PKG_VERSION").to_string(),
        ok,
        checks,
    }
}

fn all_checks_ok(checks: &[CheckRow]) -> bool {
    !checks.iter().any(|check| check.status == CheckStatus::Fail)
}

src/commands/doctor.rs:40–64

Pure Invariant

all_checks_ok establishes the strict contract rule: ok === true if and only if zero checks have status: "fail". Warnings (such as port conflicts in ports_check) never cause ok to become false.

Logs: clean facade

logs.rs resolves a target Connection ID to its unit name and delegates journal fetching to the journal adapter:

pub(crate) fn logs(config: &Config, id: &str, lines: u32) -> Result {
    let unit = resolve_unit(config, id)?;
    Ok(journal::dump(&unit, lines)?)
}

fn resolve_unit(config: &Config, id: &str) -> Result {
    let connection =
        config::by_id(config, id).ok_or_else(|| LogsCommandError::UnknownId(id.to_string()))?;
    model::unit_name(&connection.id).map_err(|source| LogsCommandError::UnitName {
        id: connection.id.clone(),
        source,
    })
}

Check yourself

  1. Why does wait_step in mutate.rs continue polling when Reconcile evaluates a single observation as ErrorCode::StartTimeout, rather than aborting immediately?
    Answer

    Reconcile's 10-second start window classifies a single snapshot in time. A proxy initializing and authenticating with Google Cloud may take slightly longer than 10 seconds to open its port, but the operator allocated a separate --wait-ms polling budget. Aborting on the first start timeout would prematurely fail slow-starting but healthy proxies.

  2. Why does unit_safely_recreatable require UnitSnapshot::Absent before restarting, rather than proceeding when Reconcile reports HealthState::Stopped?
    Answer

    Reconcile reports Stopped as soon as a deactivating unit's port closes, but systemd still holds the unit definition in memory while teardown completes. Issuing StartTransientUnit while the unit is still loaded results in a D-Bus UnitExists error, so restart must wait until systemd fully unloads it.

  3. Why does doctor() continue executing its remaining checks when config::load() fails, whereas every mutating command aborts immediately?
    Answer

    Doctor is an exploratory preflight tool designed to diagnose system health comprehensively in a single run. An invalid config file is recorded as a failure for the config check, but testing the proxy binary, D-Bus connection, ADC credentials, and journal access provides valuable diagnostic information to the operator.
