Chapter 07 · Part III

Talking to systemd

How cloud-sql-tracker supervises background database proxies as transient systemd services over native D-Bus IPC, avoiding subprocess shell-outs and unmanaged background daemons.

The native Linux supervision model

In Chapter 03, we saw that cloud-sql-tracker is a stateless CLI rather than a long-lived daemon. When an operator starts a Connection, the CLI does not spawn a background thread or detach a child process using fork-and-forget. Instead, it delegates process lifecycle management directly to the Linux service manager.

To understand how this works in code, we need four foundational Linux concepts:

  • systemd --user: A per-user instance of systemd that manages user session services. Unlike the system-wide service manager (PID 1), it runs unprivileged within the user's session and manages background jobs tied to that user.
  • D-Bus: The standard Linux inter-process communication (IPC) system. It provides a structured, object-oriented message bus where programs invoke methods and inspect properties on registered services.
  • zbus: A pure-Rust D-Bus crate that provides type-safe, high-performance synchronous and asynchronous connections to the D-Bus daemon.
  • transient unit: A dynamic systemd service created in-memory at runtime via D-Bus (cloud-sql-proxy-<id>.service) rather than read from persistent unit files on disk in ~/.config/systemd/user/.

Why native D-Bus over systemctl shell-outs

As documented in ADR 0004 and research brief docs/research/supervisor-io.md, the project evaluated two ways to interact with systemd:

  1. Shelling out to CLI binaries: spawning systemd-run --user and parsing systemctl --user show text output.
  2. Communicating natively over D-Bus using zbus.
Why

Pick: Use native D-Bus calls via zbus on the user session bus.
Why: D-Bus provides strongly-typed properties (such as MainPID: u32 and integer microsecond timestamps) and explicit error variants (such as NoSuchUnit). Shelling out to systemctl show requires fragile string parsing, spawns subprocesses on every check, and suffers from misleading exit codes—for example, systemctl show exits with status 0 even when a unit does not exist!
Discarded: Subprocess shell-outs to systemd-run / systemctl, and speculative traits like trait Supervisor.
Unchanged: journalctl remains a subprocess shell-out for logs, because text log streaming is already its native interface.

The implementation in src/supervisor.rs defines the standard D-Bus destination and interface constants:

Starting a proxy: start_transient

To start a proxy, start_transient calls the systemd manager's StartTransientUnit method. Before it can do that safely, however, it must address a subtle systemd lifecycle quirk.

The UnitExists Gotcha

When a transient unit crashes or fails, systemd does not immediately unload it from memory; it keeps the unit in state ActiveState=failed. If the operator subsequently calls StartTransientUnit with that same unit name, systemd rejects the call with an error: UnitExists. To prevent this, start_transient best-effort invokes ResetFailedUnit first, clearing any residual failure state.

Here is the full start_transient implementation in src/supervisor.rs:

/// Start `connection`'s Proxy as a transient `Type=exec` Unit
/// (`docs/research/supervisor-io.md`, "v1 D-Bus calls", `start_transient`).
///
/// `env` is the already-resolved environment to forward (e.g. `HOME`,
/// `GOOGLE_APPLICATION_CREDENTIALS`) — this module does not resolve ADC or
/// `PATH` itself; that is `env`'s job (`docs/modules.v1.md`, "env").
///
pub(crate) fn start_transient(
    connection: &Connection,
    proxy_bin: &Path,
    env: &[(String, String)],
) -> Result<(), SupervisorError> {
    let unit = model::unit_name(&connection.id)?;
    let conn = connect()?;
    let manager = manager_proxy(&conn)?;

    // A Unit that ended up `ActiveState=failed` (crash, exec failure, ...)
    // stays loaded until something clears it — `StartTransientUnit` then
    // rejects the same unit name with systemd's `UnitExists`. `stop`
    // already clears this after a successful `StopUnit`
    // (`docs/modules.v1.md`, "supervisor": "reset-failed after stop (and
    // on restart)"), but a plain `start` on a Connection nobody stopped
    // first (e.g. right after the proxy crashed on its own) never goes
    // through `stop`. Best-effort here too: a failed reset must not abort
    // the start attempt — `StartTransientUnit` below is the call that
    // actually needs to succeed.
    let _: Result<(), zbus::Error> = manager.call("ResetFailedUnit", &(unit.as_str(),));

    let exec_start: Vec<(String, Vec, bool)> = vec![(
        proxy_bin.display().to_string(),
        proxy_argv(connection, proxy_bin),
        false,
    )];
    let environment: Vec = env.iter().map(|(k, v)| format!("{k}={v}")).collect();

    let properties: Vec<(&str, Value<'_>)> = vec![
        (
            "Description",
            Value::new(format!("Cloud SQL Auth Proxy ({})", connection.id)),
        ),
        ("Type", Value::new("exec")),
        ("KillMode", Value::new("control-group")),
        ("TimeoutStopUSec", Value::new(TIMEOUT_STOP_USEC)),
        ("Restart", Value::new("no")),
        ("Environment", Value::new(environment)),
        ("ExecStart", Value::new(exec_start)),
    ];
    let aux: Vec<(&str, Vec<(&str, Value<'_>)>)> = Vec::new();

    manager
        .call::<_, _, OwnedObjectPath>(
            "StartTransientUnit",
            &(unit.as_str(), "fail", properties, aux),
        )
        .map_err(SupervisorError::Call)?;
    Ok(())
}

The transient unit properties explained

Every D-Bus property passed in properties enforces a deliberate operational constraint:

Property Value Purpose & Operational Rationale
Description Cloud SQL Auth Proxy (<id>) Human-readable string appearing in system logs and journal entries.
Type "exec" Unlike Type=simple (which reports immediate start before executing), Type=exec delays reporting success until systemd has executed the binary via execve. If the binary is missing or lacks executable permissions, start fails immediately.
KillMode "control-group" When stopping the unit, systemd signals all processes in the unit's cgroup, ensuring any child helpers or shell wrappers are cleanly terminated.
TimeoutStopUSec 30_000_000 (30s) Grace period between sending SIGTERM and forcing process termination with SIGKILL.
Restart "no" Systemd will never restart a crashed proxy automatically. Crashes remain visible as error in the status report until the operator investigates.
Environment ["HOME=...", ...] Forwards necessary environment variables, such as GOOGLE_APPLICATION_CREDENTIALS (ADC), into the spawned proxy environment.
ExecStart a(sasb) structure The command specification: binary path, argument vector, and a boolean indicating whether exit code errors are ignored (false).

Building the proxy argv: proxy_argv

When systemd executes the proxy binary, it runs the exact argument vector constructed by proxy_argv:

/// Always appended exactly once by [`proxy_argv`], even if `extra_args`
/// already repeats it.
const EXIT_ZERO_ON_SIGTERM: &str = "--exit-zero-on-sigterm";

/// The proxy argv for `ExecStart`, in the order
/// `docs/research/supervisor-io.md` ("v1 D-Bus calls", `ExecStart`)
/// specifies. `argv[0]` is always the absolute binary path (`execve`
/// convention). `--auto-iam-authn` is not in that doc's template but is a
/// frozen config flag (`docs/config.v1.md`, "Connection fields",
/// `auto_iam_authn`) — grouped with the other boolean flags.
fn proxy_argv(connection: &Connection, proxy_bin: &Path) -> Vec {
    let mut argv = vec![
        proxy_bin.display().to_string(),
        format!("--address={}", connection.address),
        format!("--port={}", connection.port),
    ];
    if connection.private_ip {
        argv.push("--private-ip".to_string());
    }
    if connection.auto_iam_authn {
        argv.push("--auto-iam-authn".to_string());
    }
    // A configured `extra_args` may already repeat this flag; keep exactly
    // one copy, immediately before the final INSTANCE argument
    // (`docs/research/supervisor-io.md`).
    argv.extend(
        connection
            .extra_args
            .iter()
            .filter(|arg| arg.as_str() != EXIT_ZERO_ON_SIGTERM)
            .cloned(),
    );
    argv.push(EXIT_ZERO_ON_SIGTERM.to_string());
    argv.push(connection.instance.clone());
    argv
}

The Clean Exit Invariant

By default, Google's cloud-sql-proxy treats SIGTERM as an abnormal termination and exits with status 143 or 1. Systemd would then record Result=exit-code and classify the unit as failed. By unconditionally appending --exit-zero-on-sigterm, the proxy exits with status code 0 on standard shutdown. As explored in Chapter 06, this is what allows Reconcile to distinguish an intentional stop from a crash.

Inspecting state: show and UnitSnapshot

When the control plane queries status via show, it queries systemd for the unit's object path and reads properties across both org.freedesktop.systemd1.Unit and org.freedesktop.systemd1.Service interfaces.

/// Everything Reconcile's clean-stop-vs-crash table needs about one Unit,
/// from a single `show` call (`docs/modules.v1.md`, "supervisor").
///
/// This module does not classify clean stop vs crash itself — that
/// judgement belongs to `reconcile` (pure), which this module does not
/// import (`docs/modules.v1.md`, "Dependency direction"). `commands` maps
/// a `Loaded` snapshot into `reconcile::UnitObservation`.
#[derive(Debug, Clone, PartialEq, Eq)]
pub(crate) enum UnitSnapshot {
    /// `LoadState=not-found`: systemd has never loaded this Unit.
    Absent,
    Loaded {
        active_state: UnitActiveState,
        /// Raw `SubState` (e.g. `running`, `dead`, `start-pre`). Diagnostic
        /// detail only — Reconcile's truth table does not branch on it.
        sub_state: String,
        /// `MainPID`; `None` when systemd reports `0` (no live process).
        main_pid: Option,
        result: UnitResult,
        exec_outcome: ExecOutcome,
        /// `ExecMainStartTimestampMonotonic`; `None` when systemd reports
        /// `0` (unknown / no start attempt yet).
        started_at_monotonic_usec: Option,
    },
}

The query logic cleanly handles missing units by catching the NoSuchUnit D-Bus error:

/// Load/missing plus everything Reconcile needs about one Unit
/// (`docs/modules.v1.md`, "supervisor").
pub(crate) fn show(unit: &UnitName) -> Result {
    let conn = connect()?;
    let manager = manager_proxy(&conn)?;

    let object_path: OwnedObjectPath = match manager.call("GetUnit", &(unit.as_str(),)) {
        Ok(path) => path,
        Err(err) if is_no_such_unit(&err) => return Ok(UnitSnapshot::Absent),
        Err(err) => return Err(SupervisorError::Call(err)),
    };

    read_snapshot(&conn, &object_path)
}

fn read_snapshot(
    conn: &zbus::blocking::Connection,
    object_path: &OwnedObjectPath,
) -> Result {
    let properties = properties_proxy(conn, object_path)?;
    let unit_props = get_all_properties(&properties, UNIT_INTERFACE)?;
    let service_props = get_all_properties(&properties, SERVICE_INTERFACE)?;

    let active_state = map_active_state(required(&unit_props, "ActiveState")?);
    let sub_state = required(&unit_props, "SubState")?;

    let main_pid = match required::(&service_props, "MainPID")? {
        0 => None,
        pid => Some(pid),
    };
    let result = map_unit_result(required(&service_props, "Result")?);
    let exec_main_code = required(&service_props, "ExecMainCode")?;
    let exec_main_status = required(&service_props, "ExecMainStatus")?;
    let started_at_monotonic_usec =
        match required::(&service_props, "ExecMainStartTimestampMonotonic")? {
            0 => None,
            usec => Some(usec),
        };

    Ok(UnitSnapshot::Loaded {
        active_state,
        sub_state,
        main_pid,
        result,
        exec_outcome: exec_outcome(exec_main_code, exec_main_status),
        started_at_monotonic_usec,
    })
}

Resilient property mapping

Systemd versions evolve over time, introducing new active states or result codes (like oom-kill in newer systemd releases). Rather than panicking or collapsing unknown strings into generic errors, src/supervisor.rs retains unrecognized values in an Unknown(String) variant:

#[derive(Debug, Clone, PartialEq, Eq)]
pub(crate) enum UnitActiveState {
    Inactive,
    Activating,
    Active,
    Deactivating,
    Failed,
    Unknown(String),
}

fn map_active_state(raw: String) -> UnitActiveState {
    match raw.as_str() {
        "inactive" => UnitActiveState::Inactive,
        "activating" => UnitActiveState::Activating,
        "active" => UnitActiveState::Active,
        "deactivating" => UnitActiveState::Deactivating,
        "failed" => UnitActiveState::Failed,
        _ => UnitActiveState::Unknown(raw),
    }
}

Similarly, the process exit signal is decoded using standard POSIX SIGCHLD codes to distinguish true exit codes from termination signals:

mod sigchld {
    pub(super) const CLD_EXITED: i32 = 1;
    pub(super) const CLD_KILLED: i32 = 2;
    pub(super) const CLD_DUMPED: i32 = 3;
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub(crate) enum ExecOutcome {
    /// `ExecMainCode == 0`: the Unit has no exec result yet.
    NotExited,
    ExitCode(i32),
    Signal(i32),
    /// An `ExecMainCode` this adapter does not know how to read.
    Unknown {
        code: i32,
        status: i32,
    },
}

fn exec_outcome(exec_main_code: i32, exec_main_status: i32) -> ExecOutcome {
    match exec_main_code {
        0 => ExecOutcome::NotExited,
        sigchld::CLD_EXITED => ExecOutcome::ExitCode(exec_main_status),
        sigchld::CLD_KILLED | sigchld::CLD_DUMPED => ExecOutcome::Signal(exec_main_status),
        code => ExecOutcome::Unknown {
            code,
            status: exec_main_status,
        },
    }
}

Stopping and health-checking: stop and systemd_user_check

Stopping a unit calls StopUnit with mode "replace". If systemd returns NoSuchUnit, the operation succeeds idempotently (a unit that was never started is already stopped). If stopping an existing unit succeeds, it also invokes ResetFailedUnit to clear stale failure counters.

/// Stop `unit` (our Unit only — never kill-by-PID) and best-effort clear its
/// failed state (`docs/modules.v1.md`, "supervisor"). A Unit systemd has
/// never loaded is already stopped: idempotent success, not an error
/// (`docs/research/supervisor-io.md`, "stop").
///
pub(crate) fn stop(unit: &UnitName) -> Result<(), SupervisorError> {
    let conn = connect()?;
    let manager = manager_proxy(&conn)?;

    match manager.call::<_, _, OwnedObjectPath>("StopUnit", &(unit.as_str(), "replace")) {
        Ok(_) => {
            // A failed reset-failed must not undo a successful stop.
            let _: Result<(), zbus::Error> = manager.call("ResetFailedUnit", &(unit.as_str(),));
            Ok(())
        }
        Err(err) if is_no_such_unit(&err) => Ok(()),
        Err(err) => Err(SupervisorError::Call(err)),
    }
}

Operational consequences: statelessness and failure recovery

The combination of transient units, Restart=no, and zero state files on disk produces clear, predictable operational behaviors:

  1. Clean reboot / shutdown: Systemd transient units exist in /run/user/<uid>/systemd/transient/ on tmpfs. When the machine shuts down or reboots, all transient units vanish completely. At next boot, no proxies restart automatically. The session begins cleanly with all connections in state stopped.
  2. Crash visibility: Because Restart="no" is configured, a proxy that crashes during a development session stays down. Systemd records ActiveState=failed, and the tracker reports Health state error. It does not enter a silent crash-restart loop that conceals configuration or credential problems.
  3. Targeted recovery: Operators recover failed proxies explicitly using cloud-sql-tracker restart --failed. This stops any lingering state, calls ResetFailedUnit, and starts a fresh transient unit.

Check yourself

  1. Why does start_transient call ResetFailedUnit on the unit before calling StartTransientUnit?
    Answer

    When a transient service fails, systemd retains the failed unit in memory; calling StartTransientUnit on an existing failed unit fails with UnitExists. ResetFailedUnit clears the residual failure state so the new transient unit can be started.

  2. Why does cloud-sql-tracker communicate with systemd via D-Bus instead of shelling out to systemctl show?
    Answer

    D-Bus provides typed properties (like MainPID: u32) and explicit error variants without subprocess overhead, whereas systemctl show requires string parsing, spawns processes, and returns exit code 0 even when a unit does not exist.

  3. What happens to running proxy units when the host machine is rebooted or experiences a sudden power loss?
    Answer

    Because transient units reside in memory on tmpfs and have Restart=no with no persisted state files, all units disappear on reboot and no proxies start automatically; every connection starts cleanly in state stopped.
