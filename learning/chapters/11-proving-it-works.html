Chapter 11 · Part V

Proving it works

How cloud-sql-tracker guarantees correctness across 276 tests: pure-seam unit tests, golden schema checks, real binary subprocess verification, and human dogfooding.

The verification ladder

A desktop infrastructure tool that controls background database proxies cannot afford flaky tests, stale mocks, or untested wire formats. If cloud-sql-tracker emits invalid JSON, the Omarchy desktop status bar breaks. If port classification misidentifies a listener PID, an operator might accidentally kill a foreign process or fail to notice a port conflict.

Rather than relying on a slow, brittle end-to-end test suite that requires live Google Cloud instances and a running systemd daemon, the project uses a four-layer verification ladder:

1. Pure-seam unit tests

The foundation of the test suite rests on pure functions. Because business logic is decoupled from system calls, edge cases can be tested exhaustively without faking complex system state.

Reconcile truth table

In Chapter 06, we saw that reconcile() accepts a Connection definition, an Observation snapshot, and an injected now: SystemTime timestamp. Because time and I/O are parameters, unit tests verify every row of the 13-row state transition table deterministically:

#[test]
fn activating_within_start_window_is_starting_without_attributed_process() {
    let unit = unit_with(
        UnitState::Activating,
        None,
        Some(now() - Duration::from_secs(5)),
    );
    let row = reconcile(
        &connection("fe-dev", 15432),
        &observe(unit, closed_port()),
        now(),
    );
    assert_eq!(row.state, HealthState::Starting);
    assert_eq!(row.source, Source::None);
    assert_eq!(row.pid, None);
}

Multi-target exit code resolution

In src/cli.rs, the pure function exit_for_batch() maps multi-connection outcomes to exit codes 0, 1, 2, 3, or 4. Unit tests prove priority ordering without running subprocesses:

2. Layer 1: Schema contract verification

Every JSON surface in the project (Status document, Doctor report, and configuration) has a matching JSON Schema in schemas/ and a golden reference in examples/. Layer 1 verifies that the golden example files strictly adhere to their JSON Schemas using a dedicated shell script:

#!/usr/bin/env bash
# Layer 1 of issue #23: golden examples vs JSON Schemas.
# This script is the pair registry. Call it from mise, hk pre-push, and CI.
set -euo pipefail

root="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$root"

check() {
  local schema="$1"
  local instance="$2"
  echo "validate '${instance}' against '${schema}'"
  check-jsonschema --schemafile "${schema}" "${instance}"
}

check schemas/status.v1.json examples/status.v1.json
check schemas/config.v1.json examples/connections.json
check schemas/doctor.v1.json examples/doctor.v1.json

3. Layer 2: Built binary stdout testing

Passing in-process Rust serialization tests (testing that serde_json::to_value(&status_doc) matches a schema) is a necessary step, but it is not sufficient. In-process tests do not prove that:

  • The compiled binary's CLI flag parsing correctly routes to the JSON formatter.
  • The output is emitted on stdout rather than corrupted by logs or error messages printed to stderr.
  • The executable exits with the exact status code specified in the CLI contract.

Layer 2 tests live in tests/cli_json_contracts.rs and tests/cli_smoke.rs. They spawn the actual compiled binary using Cargo's environment variable env!("CARGO_BIN_EXE_cloud-sql-tracker") and validate raw stdout bytes against JSON Schemas using the jsonschema crate.

fn bin() -> Command {
    Command::new(env!("CARGO_BIN_EXE_cloud-sql-tracker"))
}

fn assert_validates(schema_relative_path: &str, instance: &serde_json::Value) {
    let schema = read_schema(schema_relative_path);
    let validator =
        jsonschema::validator_for(&schema).expect("compile schema (checked in and Layer-1-clean)");
    let errors: Vec = validator
        .iter_errors(instance)
        .map(|error| format!("{}: {error}", error.instance_path()))
        .collect();
    assert!(
        errors.is_empty(),
        "{schema_relative_path} rejected instance:\n{}\n\ninstance:\n{}",
        errors.join("\n"),
        serde_json::to_string_pretty(instance).unwrap_or_default(),
    );
}

The headless CI challenge: zero vs non-zero connections

When status --json runs with configured connections, it attempts to query systemd over D-Bus via zbus. However, some CI runners (such as minimal container environments or SSH runners) lack an active systemd user bus.

To ensure CI never skips Layer 2 validation while remaining green across different runner environments, the test suite splits into two distinct integration tests:

  1. Unconditional Zero-Connections Test: A configuration with "connections": [] produces a valid Status document without ever calling D-Bus or socket probes. This test must always pass with exit code 0 on every environment: 
    #[test]
fn status_json_stdout_with_zero_connections_validates_against_the_status_schema() {
    let config = ConfigFixture::write(EMPTY_CONFIG);
    let output = bin()
        .args(["--config", config.path().to_str().unwrap(), "status", "--json"])
        .output()
        .expect("spawn the binary");

    assert_eq!(output.status.code(), Some(0));
    let instance = parse_stdout_json(&output.stdout);
    assert_validates("schemas/status.v1.json", &instance);
    assert_eq!(instance["total"], 0);
}

    tests/cli_json_contracts.rs:136–160

  2. Populated Connections Test with Graceful Dependency Handling: When testing populated connection arrays, if the environment completely lacks a systemd user manager, the CLI exits with code 3 (Dependency Failure). The test inspects stderr: if the exit is genuinely due to an absent bus, it logs a skip; but if the bus responded and returned malformed data (a schema regression), the test panics: 
    #[test]
fn status_json_stdout_validates_against_the_status_schema() {
    let config = ConfigFixture::write(MINIMAL_CONFIG);
    let output = bin()
        .args(["--config", config.path().to_str().unwrap(), "status", "--json"])
        .output()
        .expect("spawn the binary");

    match output.status.code() {
        Some(0) => {
            let instance = parse_stdout_json(&output.stdout);
            assert_validates("schemas/status.v1.json", &instance);
        }
        Some(3) if stderr_indicates_no_systemd_user_manager(&output.stderr) => {
            eprintln!("SKIP (environment): no systemd user manager reachable");
        }
        other => panic!("unexpected exit {other:?} for status --json"),
    }
}

5. Case study: the ETXTBSY parallelism flake

Lesson learned

Do not guess at root causes. When implementing the proxy_bin version probe, tests creating temporary shell scripts began intermittently failing with Text file busy (os error 26) during parallel cargo test runs.

A code reviewer initially claimed that flushing writes with fsync and performing an atomic rename would fix the issue. However, empirical measurement proved the reviewer wrong: main was 10/10 clean, but the change failed 5 out of 10 runs even with atomic renames.

The actual Linux kernel behavior: execve() returns ETXTBSY if any thread in the entire process holds a writable file descriptor or memory mapping to that inode. Because Rust's test harness executes unit tests as multiple concurrent OS threads within a single process, writing temporary scripts in one test raced with execve() calls in another test.

The architectural rule established from this incident (Issue #82):

  1. Keep production code clean: In production, cloud-sql-proxy is never written by the tracker CLI, so production code uses a single, plain Command::spawn() with zero retry loops.
  2. Isolate test workarounds to test code: The retry logic was placed strictly inside #[cfg(test)] helper functions:
#[cfg(test)]
fn probe_proxy_version_for_test(path: &Path) -> Result {
    const ATTEMPTS: usize = 3;
    const BACKOFF: Duration = Duration::from_millis(5);
    let mut last = None;
    for _ in 0..ATTEMPTS {
        match probe_proxy_version(path) {
            Err(ProxyVersionError::SpawnFailed { detail })
                if detail.contains("Text file busy") =>
            {
                last = Some(ProxyVersionError::SpawnFailed { detail });
                std::thread::sleep(BACKOFF);
            }
            other => return other,
        }
    }
    Err(last.expect("loop runs at least once"))
}

6. The human dogfood gate

Automated tests verify contracts and logic, but they cannot verify real-world developer ergonomics, desktop notification interaction, or actual database network packets. Before closing the v1 implementation milestone (Map #28), the operator completed a strict human verification checklist on a live Arch Linux workstation (Issue #46):

Checklist Item Verification Method Outcome
Preflight health Run cloud-sql-tracker doctor Passed with ok: true, resolving proxy v2.25.2 and valid ADC.
All 7 proxies Execute cloud-sql-tracker start --all All 7 transient units created; ports 15432–15438 listening.
Real traffic Connect via DBeaver / psql to each group Queries executed successfully through local ports.
Journal logs Run cloud-sql-tracker logs fe-dev Correct systemd user journal entries printed to stdout.
Clean stop Execute cloud-sql-tracker stop --all All transient units terminated with SIGTERM (exit code 0).

Check yourself

  1. Why are in-process serde serialization tests insufficient to prove Layer 2 contract compliance?
    Answer

    In-process serde tests only prove that Rust data structures match a schema, but cannot prove that the compiled binary parses CLI arguments correctly, emits valid JSON directly to stdout without stderr pollution, or exits with the right process exit code.

  2. How does the test suite ensure Layer 2 tests run reliably in CI environments without a systemd user daemon?
    Answer

    The suite uses an unconditional test with zero connections that requires no D-Bus calls, while allowing tests with populated connections to gracefully skip only when stderr confirms the user bus is unreachable.

  3. Why was the ETXTBSY retry logic placed inside #[cfg(test)] rather than inside production spawn code?
    Answer

    Production never writes proxy executables so it cannot trigger file-busy errors, whereas the multi-threaded test runner creates and executes temporary script files concurrently across test threads.
