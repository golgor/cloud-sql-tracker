Chapter 05 · Part II

The model and the config

Data types establish our shared domain vocabulary; strict parsing and layered validation guarantee that invalid configuration never reaches the runtime.

Types before behavior

Every long-lived program develops a vocabulary. In poorly structured software, that vocabulary lives in ad-hoc strings, loose tuples, and scattered dictionary lookups. In cloud-sql-tracker, the vocabulary lives in src/model.rs as distinct Rust structs and enums.

As established in Chapter 02, domain terms like Connection, Health state, and Unit are not loose abstractions. They are concrete types. src/model.rs contains no I/O, no network calls, and no CLI parsing logic. It is the single place in the codebase that pairs internal Rust data structures with their serialized wire representations.

Naming systemd units safely

On Linux, systemd supervises background services using units—configuration entities that represent processes, sockets, or devices. A transient unit is a service unit created dynamically at runtime via systemd's D-Bus API rather than loaded from a static file on disk.

Every connection managed by the CLI corresponds to one transient systemd user service named cloud-sql-proxy-<id>.service. To ensure that unit names are assembled consistently across all modules, src/model.rs encapsulates this logic in a transparent newtype, UnitName:

/// The systemd `--user` unit name for one Connection's managed Proxy process.
///
/// Always `cloud-sql-proxy-<sanitized-id>.service`. `supervisor`, `journal`,
/// and the Status `unit` field all go through [`unit_name`] so the string is
/// assembled in exactly one place.
///
/// `#[serde(transparent)]`: a `UnitName` is always a plain string on the
/// wire (e.g. the Status document's `unit` field) — never the newtype
/// wrapper.
#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize)]
#[serde(transparent)]
pub(crate) struct UnitName(String);

impl UnitName {
    pub(crate) fn as_str(&self) -> &str {
        &self.0
    }
}

const MAX_UNIT_NAME_LEN: usize = 255;

/// The systemd `.service` unit name for a Connection id.
pub(crate) fn unit_name(id: &str) -> Result<UnitName, UnitNameError> {
    let core = if is_config_valid_id(id) {
        id.to_string()
    } else {
        sanitize_unit_id(id)?
    };
    let name = format!("cloud-sql-proxy-{core}.service");
    if name.len() > MAX_UNIT_NAME_LEN {
        return Err(UnitNameError::TooLong {
            len: name.len(),
            max: MAX_UNIT_NAME_LEN,
        });
    }
    Ok(UnitName(name))
}

src/model.rs:20–70

Why valid IDs are preserved without sanitization

A connection ID that satisfies the config rules (^[a-zA-Z0-9][a-zA-Z0-9_-]*$) is already valid in systemd unit names. If unit_name() unconditionally ran sanitization (such as collapsing repeated dashes), two distinct connection IDs like fe--dev and fe-dev would collapse into the exact same systemd unit name. Preserving valid IDs avoids namespace collisions.

Finding and loading configuration

Configuration loading lives in src/config.rs. By default, the control plane looks for its configuration file under the standard XDG path:

/// `$XDG_CONFIG_HOME/cloud-sql-tracker/connections.json`, else
/// `~/.config/cloud-sql-tracker/connections.json`.
#[allow(dead_code)]
pub(crate) fn default_path() -> PathBuf {
    let config_home = std::env::var("XDG_CONFIG_HOME")
        .ok()
        .filter(|value| !value.is_empty())
        .map(PathBuf::from)
        .unwrap_or_else(|| home_dir().join(".config"));
    config_home
        .join("cloud-sql-tracker")
        .join("connections.json")
}

fn home_dir() -> PathBuf {
    PathBuf::from(std::env::var("HOME").unwrap_or_default())
}

/// Runtime Connection inventory after load, merge, and validation.
#[derive(Debug, Clone, PartialEq, Eq)]

    pub(crate) proxy_bin: String,
    pub(crate) connections: Vec<Connection>,

/// Read `path` then [`parse`] its bytes.
pub(crate) fn load(path: &Path) -> Result<Config, ConfigError> {
    let bytes = std::fs::read(path).map_err(|source| ConfigError::Io {
        path: path.to_path_buf(),
        source,
    })?;
    parse(&bytes)
}

Pure Parsing Seam

Notice the architectural separation: load() handles the filesystem read, while parse() is completely pure. This allows every parsing and validation test in the test suite to run in memory without creating temporary files or touching disk.

The 3-tier merge hierarchy

A user's connections.json configuration combines global defaults and per-connection overrides. To process this cleanly, src/config.rs defines raw deserialization structs using Serde's deny_unknown_fields attribute:

/// Raw shapes mirroring `schemas/config.v1.json`. Unknown keys are
/// rejected at every level (`docs/config.v1.md`, "Strict keys").
#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
struct RawConfig {
    version: i64,
    proxy_bin: Option<String>,
    defaults: Option<RawDefaults>,
    connections: Vec<RawConnection>,
}

#[derive(Debug, Deserialize, Default)]
#[serde(deny_unknown_fields)]
struct RawDefaults {
    address: Option<String>,
    private_ip: Option<bool>,
    auto_iam_authn: Option<bool>,
    extra_args: Option<Vec<String>>,
    enabled: Option<bool>,
}

#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
struct RawConnection {
    id: String,
    name: String,

Every connection undergoes a strict three-tier merge order:

Built-in Defaults (Hardcoded in binary) │ address = "127.0.0.1", private_ip = false, auto_iam_authn = false, extra_args = [], enabled = true ▼ File-level Defaults (`defaults` block in JSON) │ Overwrites built-in defaults with file-wide settings ▼ Connection Object (`connections[]` entry in JSON) │ Overwrites file-level defaults with per-target specifics ▼ Final Validated Connection

Here is how the merge is executed in Rust:

const DEFAULT_PROXY_BIN: &str = "cloud-sql-proxy";
const DEFAULT_ADDRESS: &str = "127.0.0.1";

/// Built-in defaults (`docs/config.v1.md`, "Built-in defaults") layered
/// under file `defaults`, then the connection object (`docs/config.v1.md`,
/// "Merge order"). Identity fields (`name`/`group`/`instance`/`port`) are
/// already required directly on `raw`; only the optional fields merge.
fn merge_connection(defaults: &RawDefaults, raw: RawConnection) -> Result<Connection, ConfigError> {
    let id = raw.id;
    validate_id(&id).map_err(|reason| invalid(&id, reason))?;
    validate_instance(&raw.instance).map_err(|reason| invalid(&id, reason))?;
    validate_port(raw.port).map_err(|reason| invalid(&id, reason))?;

    Ok(Connection {
        id,
        name: raw.name,
        group: raw.group,
        instance: raw.instance,
        address: raw
            .address
            .or_else(|| defaults.address.clone())
            .unwrap_or_else(|| DEFAULT_ADDRESS.to_string()),
        port: raw.port,
        private_ip: raw.private_ip.or(defaults.private_ip).unwrap_or(false),
        auto_iam_authn: raw
            .auto_iam_authn
            .or(defaults.auto_iam_authn)
            .unwrap_or(false),
        extra_args: raw
            .extra_args
            .or_else(|| defaults.extra_args.clone())
            .unwrap_or_default(),
        enabled: raw.enabled.or(defaults.enabled).unwrap_or(true),
    })
}

src/config.rs:173–204

Identity Fields Are Not Defaultable

Notice that id, name, group, instance, and port are required fields on RawConnection and do not exist on RawDefaults. Allowing identity fields in global defaults would make duplicate IDs and ports almost inevitable.

Validation as a hard error

Silent configuration decay is a primary source of operational outages. If a configuration file contains a typo like "prot": 15432, a permissive parser might ignore it and fall back to default ports. cloud-sql-tracker enforces strict validation so that any ambiguity fails fast at load time with exit code 2.

1. Unknown fields are rejected

Because RawConfig, RawDefaults, and RawConnection all carry #[serde(deny_unknown_fields)], any unrecognised JSON key triggers a deserialization failure immediately.

2. Format and shape checks

Each field is checked against exact domain constraints:

const RESERVED_PORTS: [u16; 3] = [1433, 3306, 5432];
const MIN_UNPRIVILEGED_PORT: u16 = 1024;
const MAX_ID_LEN: usize = 64;

/// `^[a-zA-Z0-9][a-zA-Z0-9_-]*$`, length 1-64 (`docs/config.v1.md`,
/// "Connection fields").
fn validate_id(id: &str) -> Result<(), String> {
    let mut chars = id.chars();
    let starts_alphanumeric = chars.next().is_some_and(|c| c.is_ascii_alphanumeric());
    let rest_is_id_safe = chars.all(|c| c.is_ascii_alphanumeric() || c == '_' || c == '-');
    if starts_alphanumeric && rest_is_id_safe && id.len() <= MAX_ID_LEN {
        Ok(())
    } else {
        Err(format!(
            "id `{id}` must match ^[a-zA-Z0-9][a-zA-Z0-9_-]*$ and be at most {MAX_ID_LEN} bytes"
        ))
    }
}

/// `project:region:instance` — three non-empty, whitespace-free segments
/// (`docs/config.v1.md`, "Connection fields").
fn validate_instance(instance: &str) -> Result<(), String> {
    let segments: Vec<&str> = instance.split(':').collect();
    let shape_ok = segments.len() == 3
        && segments
            .iter()
            .all(|segment| !segment.is_empty() && !segment.chars().any(char::is_whitespace));
    if shape_ok {
        Ok(())
    } else {
        Err(format!(
            "instance `{instance}` must be project:region:instance (three non-empty segments)"
        ))
    }
}

/// 1024-65535, excluding the reserved set (`docs/config.v1.md`,
/// "Reserved ports").
fn validate_port(port: u16) -> Result<(), String> {
    if port < MIN_UNPRIVILEGED_PORT {
        Err(format!(
            "port {port} is privileged (must be >= {MIN_UNPRIVILEGED_PORT})"
        ))
    } else if RESERVED_PORTS.contains(&port) {
        Err(format!("port {port} is reserved"))
    } else {
        Ok(())
    }
}

src/config.rs:211–255

3. Reserved port protection

Ports 1–1023 are privileged system ports. Ports 5432 (PostgreSQL), 3306 (MySQL), and 1433 (SQL Server) are the standard database ports. Why does the CLI forbid them? Because the entire purpose of cloud-sql-tracker is to provide stable, non-conflicting local proxies that do not collide with local Docker Compose stacks or native database engines running on their default ports.

4. Global uniqueness validation

Once all connections are parsed and merged, src/config.rs ensures that there are no duplicate IDs, local ports, or remote Cloud SQL instances across the entire file:

/// Unique `id`, `port`, and `instance` across the whole file
/// (`docs/config.v1.md`, "Uniqueness").
fn check_uniqueness(connections: &[Connection]) -> Result<(), ConfigError> {
    let mut seen_ids = HashSet::new();
    let mut seen_ports = HashSet::new();
    let mut seen_instances = HashSet::new();

    for connection in connections {
        if !seen_ids.insert(connection.id.clone()) {
            return Err(ConfigError::DuplicateId(connection.id.clone()));
        }
        if !seen_ports.insert(connection.port) {
            return Err(ConfigError::DuplicatePort(connection.port));
        }
        if !seen_instances.insert(connection.instance.clone()) {
            return Err(ConfigError::DuplicateInstance(connection.instance.clone()));
        }
    }
    Ok(())
}

Check yourself

  1. Why does unit_name() check is_config_valid_id() and bypass sanitization for valid IDs rather than running all IDs through character replacement and dash collapsing?
    Answer

    A config-valid ID already meets all systemd naming requirements. Bypassing sanitization prevents distinct IDs like a--b and a-b from collapsing into the exact same systemd unit name and colliding.

  2. Why are default database ports (5432, 3306, 1433) treated as reserved and rejected during port validation?
    Answer

    Rejecting default database ports prevents proxy endpoints from colliding with local Docker Compose containers or native database servers that developers frequently run on default standard ports.

  3. What is the three-layer merge hierarchy applied to optional connection fields, and why are identity fields excluded from the defaults object?
    Answer

    Optional properties merge built-in defaults, then file-level defaults, then per-connection overrides. Identity fields like ID and port cannot be defaulted because each connection requires globally unique identity values.
