Chapter 01 · Part I

The problem

Understand the real-world operational friction that created cloud-sql-tracker, what this control plane owns, and what it deliberately delegates to Google.

The developer desktop before this tool

Modern cloud development often requires connecting local development tools—like DBeaver, psql, and application servers—to several remote managed databases in Google Cloud SQL. Google provides an official tunneling binary called the Cloud SQL Auth Proxy (cloud-sql-proxy), which establishes secure, authenticated, encrypted TCP tunnels to remote instances without requiring public IP allowlisting.

In practice, developers typically manage these proxies through ad-hoc shell commands or one-line scripts:

# Typical developer one-liner:
cloud-sql-proxy my-project:europe-west1:backend-postgres-1

Running proxies this way introduces three severe operational pain points on a local Linux workstation:

  1. Port collisions on 5432: By default, each proxy instance binds to PostgreSQL's default port (5432), MySQL's (3306), or SQL Server's (1433). The moment a developer needs to connect to two databases at once—or runs local Docker Compose environments—the second proxy crashes with a port-binding error.
  2. No shared status surface: When a proxy runs in a hidden terminal tab, background script, or disconnected shell session, the operator has no single place to inspect which proxies are active, which ports they occupy, or why a database connection suddenly refused traffic.
  3. Unmanaged process lifecycles: Killing terminal windows or restarting the desktop shell often leaves orphan proxy processes running in the background, silently holding local ports and blocking subsequent start attempts.
Why

Defaulting to port 5432 creates immediate friction in environments running local Docker containers. cloud-sql-tracker assigns a fixed, non-default port (such as 15432, 15433, 15434) to every configured database connection, isolating cloud database tunnels from local container stacks.

What cloud-sql-tracker owns (and refuses to own)

To solve this without creating unnecessary complexity, cloud-sql-tracker acts strictly as a control plane. It manages configuration, process supervision, health aggregation, and structured status reporting:

┌────────────────────────────────────────────────────────┐ │ UI / Bar Plugin / Terminal Scripts │ └───────────────────────────┬────────────────────────────┘ │ argv + stdout JSON only ▼ ┌────────────────────────────────────────────────────────┐ │ cloud-sql-tracker (Stateless Rust Control Plane) │ │ - Parses ~/.config/cloud-sql-tracker/connections.json │ │ - Supervises systemd --user transient units │ │ - Emits versioned Status Document (status --json) │ └───────────────────────────┬────────────────────────────┘ │ D-Bus / zbus ▼ ┌────────────────────────────────────────────────────────┐ │ systemd --user │ │ └─ cloud-sql-proxy-fe-dev.service │ │ └─ exec: cloud-sql-proxy (Google Binary) │ └────────────────────────────────────────────────────────┘

A few core concepts define this architecture:

  • systemd unit: A configuration entity managed by systemd, Linux's system and service manager. Our proxies run as user-level services.
  • transient unit: A dynamic systemd service created in-memory at runtime via D-Bus (cloud-sql-proxy-<id>.service) rather than written to persistent disk files in ~/.config/systemd/user/.
  • D-Bus: The standard Linux inter-process communication mechanism. The control plane communicates with systemd's user instance over D-Bus via the pure-Rust zbus crate.
  • Application Default Credentials (ADC): Google's standard credential discovery pattern (usually initialized with gcloud auth application-default login), which the proxy binary requires to authenticate with Google APIs.
The architectural boundary

cloud-sql-tracker does not tunnel database traffic. Google's stock cloud-sql-proxy binary owns the data plane. The tracker only supervises the processes, verifies local listener availability, and formats status.

The companion desktop plugin

The control plane was built to support both command-line terminal workflows and desktop panel integrations. The companion status bar widget (cloud-sql-tracker-oma-plugin) lives in a completely separate repository designed for the Omarchy desktop environment (built on Quickshell and QML).

The separation is rigorous: the bar widget has no direct access to configuration files and maintains no internal process state. Every 1–2 seconds, the widget runs cloud-sql-tracker status --json, parses the stdout JSON stream, and renders active database groups. Clicking a toggle invokes cloud-sql-tracker start <id> or cloud-sql-tracker stop <id>.

Check yourself

  1. Why does cloud-sql-tracker enforce non-default ports (like 15432) instead of defaulting to standard database ports like 5432?
    Answer

    Default database ports like 5432 collide with local database instances or Docker Compose containers, and prevent running multiple cloud proxy instances simultaneously on one machine.

  2. What is the division of responsibility between the data plane and the control plane in this system?
    Answer

    The data plane is Google's official proxy binary which handles encrypted database tunneling, while the control plane is this CLI which supervises processes, checks ports, and aggregates status.

  3. How does the Omarchy bar widget discover the status of active cloud SQL connections?
    Answer

    The desktop widget periodically executes the CLI with the status --json flag and parses stdout JSON, without accessing configuration files or managing process lifecycles directly.
