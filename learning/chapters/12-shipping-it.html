Chapter 12 · Part V

Shipping it

From source code to a hardened release binary on the operator's PATH: toolchain pinning, release profile optimization, automated GitHub Releases, and operational shutdown semantics.

The journey to production

Building a correct Rust program is only half the engineering challenge; shipping it predictably to an operator's workstation is the other half. In cloud-sql-tracker, shipping encompasses four tightly coordinated concerns:

  1. Toolchain reproducibility: Ensuring developer machines and CI runners execute identical compiler versions and lint rules.
  2. Binary optimization: Tuning compiler profile flags to minimize binary size while preserving execution speed and error diagnostics.
  3. Automated release artifacts: Packaging versioned archives and cryptographic checksums on Git tag pushes without manual intervention.
  4. Operational lifecycle: Defining how the compiled binary behaves when the host operating system restarts, logs out, or loses power.

1. The "one number in three files" rule

To eliminate discrepancies between local development and CI pipelines, the Rust toolchain version is locked to a single exact version—1.97.1—across three configuration files simultaneously:

┌────────────────────────────────────────────────────────┐ │ 1. mise.toml (Local Developer Toolchain Manager) │ │ [tools] rust = { version = "1.97.1", ... } │ └───────────────────────────┬────────────────────────────┘ │ ┌───────────────────────────▼────────────────────────────┐ │ 2. Cargo.toml (Minimum Supported Rust Version - MSRV) │ │ [package] rust-version = "1.97.1" │ └───────────────────────────┬────────────────────────────┘ │ ┌───────────────────────────▼────────────────────────────┐ │ 3. .github/workflows/ci.yml & release.yml (GitHub CI) │ │ env: RUST_VERSION: "1.97.1" │ └────────────────────────────────────────────────────────┘

If a developer upgrades their local compiler, mise ensures they continue compiling with 1.97.1. If someone introduces a Rust feature from version 1.98.0, Cargo fails during cargo check. When the project decides to bump its compiler version, all three files are updated in a single commit.

2. Local task automation with mise

The project uses mise as a thin task runner. Rather than inventing proprietary build abstractions, every mise task is a transparent wrapper around standard Cargo commands:

[tasks.fmt]
description = "Format Rust sources"
run = "cargo fmt"

[tasks.lint]
description = "Clippy with warnings denied"
run = "cargo clippy --all-targets --all-features -- -D warnings"

[tasks.test]
description = "Default cargo test (never --include-ignored)"
run = "cargo test"

[tasks.check]
description = "Full local gate (matches CI)"
run = [
  "mise run fmt-check",
  "mise run lint",
  "mise run test",
  "mise run contracts",
]

Symlinking for active dogfooding

During active development, running cargo install --path . compiles the binary and copies it into ~/.cargo/bin/. However, this creates friction: after making a code change, the developer must remember to reinstall the binary, or risk testing a stale version.

The project solves this with the install-local task, which compiles an optimized release build and establishes a symbolic link in ~/.local/bin/ directly pointing to the target build artifact:

# Symlink keeps PATH pointed at this worktree's target/release binary after each rebuild.
[tasks.install-local]
description = "Build release and symlink into ~/.local/bin for PATH dogfood"
run = """
#!/usr/bin/env bash
set -euo pipefail
mise run build-release
mkdir -p "${HOME}/.local/bin"
ln -sfn "${PWD}/target/release/cloud-sql-tracker" "${HOME}/.local/bin/cloud-sql-tracker"
echo "linked ${HOME}/.local/bin/cloud-sql-tracker -> ${PWD}/target/release/cloud-sql-tracker"
"${HOME}/.local/bin/cloud-sql-tracker" --version
"""

mise.toml:47–60

Why

Immediate iteration: With a symlink in place, running mise run build-release immediately updates the binary invoked by the shell and the desktop status bar plugin without touching file locations or permissions.

3. Release profile & binary size economics

Because the CLI is invoked every 1–2 seconds by the Omarchy status bar, binary size and execution speed matter. Research conducted in docs/research/release-build.md measured various release profile configurations on an x86_64 Linux workstation:

Profile Configuration Binary Size Delta vs Baseline Architectural Decision
Baseline (LTO + 1 Codegen Unit + Strip) 2,711,184 B (2.59 MiB) 0% PICK (Optimal balance of size & speed)
opt-level = "z" (Optimize for size) 1,885,584 B (1.80 MiB) -30.5% Discarded (Sacrifices execution speed)
panic = "abort" (Remove unwinding) 2,302,736 B (2.20 MiB) -15.1% Discarded (Weakens panic diagnostics)
lto = "thin" (Thin LTO) 2,968,632 B (2.83 MiB) +9.5% Discarded (Larger binary than fat LTO)
strip = false (Keep debug info) 5,568,944 B (5.31 MiB) +105.0% Discarded (Debuginfo unnecessary in release)
Default Release (No LTO, 16 Codegen Units) 3,851,904 B (3.67 MiB) +42.1% Discarded (Misses dead-code elimination)

The project pinned the following release profile in Cargo.toml:

[profile.release]
lto = true
codegen-units = 1
strip = true

Cargo.toml:32–35

Here is what each knob accomplishes:

  • lto = true (Fat Link-Time Optimization): LLVM performs cross-crate dead-code elimination and aggressive inlining across the entire dependency graph at link time.
  • codegen-units = 1: Forces LLVM to process the crate as a single unit rather than splitting it across 16 parallel threads, maximizing global optimization opportunities.
  • strip = true: Automatically strips symbol tables and debug symbols during compilation, eliminating the need for a separate strip(1) step.
UPX Packing Discarded

Packing executables with UPX was explicitly rejected. For a security-sensitive binary managing database credentials and systemd services, runtime decompression hurts transparency, triggers antivirus heuristics, and adds startup overhead.

The single version source & lockfile trap

The version number is declared in exactly one place: Cargo.toml under [package].version. The CLI binary reads this at compile time via env!("CARGO_PKG_VERSION"). There is no second hardcoded constant in main.rs.

Lesson learned

Always update Cargo.lock with version bumps: During the release of v0.1.1 (Issue #79), Cargo.toml was bumped from 0.1.0 to 0.1.1, but Cargo.lock was not regenerated in the same commit. When the CI release workflow ran cargo test --locked, Cargo detected that Cargo.lock was out of date and failed the build after the tag was already pushed.

5. Operational shutdown & restart behavior

What happens when the developer's computer shuts down, reboots, or crashes? The system behavior is governed by systemd transient unit semantics and ADR 0001:

let properties: Vec<(&str, Value<'_>)> = vec![
    (
        "Description",
        Value::new(format!("Cloud SQL Auth Proxy ({})", connection.id)),
    ),
    ("Type", Value::new("exec")),
    ("KillMode", Value::new("control-group")),
    ("TimeoutStopUSec", Value::new(TIMEOUT_STOP_USEC)),
    ("Restart", Value::new("no")),
    ("Environment", Value::new(environment)),
    ("ExecStart", Value::new(exec_start)),
];

Graceful shutdown vs hard power cut

Event System Action Proxy Exit Code Reconcile Interpretation
Graceful Logout / Reboot systemd sends SIGTERM to the proxy's control group Exits 0 (due to --exit-zero-on-sigterm) Clean stop → HealthState::Stopped
Proxy Crash / Panic Process terminates abnormally Non-zero exit code / Signal Unit failed → HealthState::Error
Hard Power Loss Kernel halts immediately; no signal sent N/A Memory cleared on reboot

Why proxies never autostart on reboot

Three independent architectural properties guarantee that proxies never automatically restart after a reboot:

  1. Transient Units: Units exist only in /run/user/<uid>/systemd/transient/ on a tmpfs RAM filesystem, which is wiped entirely on reboot. No static unit files are written to ~/.config/systemd/user/.
  2. Restart=no: Systemd is explicitly instructed never to restart an exited proxy unit.
  3. Statelessness (ADR 0001): The control plane maintains no database or desired-state file. When the system boots, all configured connections are cleanly reported as stopped until the operator or bar widget explicitly requests a start.
Payoff

Zero stale state: Because there are no PID files or state databases, an unexpected power outage leaves behind zero corrupt state. The next boot starts with a completely clean slate.

Check yourself

  1. Why does cloud-sql-tracker enforce the same Rust toolchain version across mise.toml, Cargo.toml, and GitHub Actions?
    Answer

    Locking the toolchain to one exact version eliminates discrepancies in compiler optimizations, Clippy lint behavior, and formatting rules between developer machines and CI runners.

  2. Why was UPX executable compression rejected for the release binary despite reducing file size?
    Answer

    UPX compression obscures binary contents, triggers security heuristics in antivirus software, and introduces runtime decompression overhead for a tool that runs frequently.

  3. Why do supervised proxy processes never automatically restart when the computer boots up?
    Answer

    Proxy services are created as transient units stored only in temporary memory with Restart=no, and the control plane maintains no persistent state files.
